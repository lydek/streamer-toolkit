# Architecture

DDD + Clean Architecture, implemented as a Modular Monolith: one program, one crate per business module, layers inside each module. Adopted progressively: DDD tactical patterns are used only in complex modules. Tech choices and adoption timing are in [decisions.en.md](decisions.en.md).

## 1. Layout
Update this section when the layout changes.

```text
crates/
  core/            # Shared core (package name `toolkit-core`, avoiding Rust's built-in `core`): settings, module registry and enable/disable controls, the chat command table, internal integration events, event envelope, in-memory event broadcast, outbox (with its own migrations)
  integrations/    # Twitch (EventSub) and OBS (obws) adapters: turn external events into internal events; handle OAuth, reconnect, backoff, rate limits
  modules/
    chat/          # Chat display (thin)
    alerts/        # Event alerts: follows, subs, Bits, raids (thin)
    redemption/    # Redemption records (complex)
    checkin/       # Daily check-in (complex): subscribes to RedemptionRecorded and chat command events
    sound/         # Sound management (thin)
    bgm/           # Background music: the music library, playlists, the player and scene rules (thin)
    counter/       # Counters: global counts, per-viewer counts and the sub marathon timer (thin; module ID `counter`, the marathon has its own switch `marathon`)
    overlays/      # Screen tools: the break / starting-soon card, on-stream warnings, the built-in overlays' look and the media library for redemptions (thin; the break card's module ID is `screen-tools`, the warnings' `warnings`, redemption videos and GIFs' `media`)
    stream/        # Live state and stream sessions (thin)
    activity/      # Activity records: follows, subs, Bits, raids (thin)
    viewers/       # Viewer directory (thin)
  host/            # Composition root: wires modules, Axum HTTP/WebSocket routes, overlay static pages
  arch-tests/      # Architecture tests only (see §7)
apps/
  desktop/         # Tauri 2 shell: starts the Host in-process, system tray, single-instance lock; the admin window loads the Host URL
  web/             # Vue 3 + TS: admin UI, overlay pages, small port-change page
```

## 2. Layers inside a module
Every module crate has three layer folders, thin modules included, so an upgrade needs no file moves.

| Layer | Contents | May depend on |
|---|---|---|
| `domain/` | Entities and rules; complex modules use Aggregate / Value Object / Domain Event | Only shared types from `core`; **must not** use `sqlx` or `axum` |
| `application/` | Use cases and ports (Repository traits, public service traits) | `domain` |
| `infrastructure/` | `db/`: SQLx Repository implementations and Rows; `http/`: Axum handlers and DTOs (OpenAPI generated); event mapping | `application`, `domain` |

- A module's `lib.rs` exposes only application service traits, public DTOs and public events; everything else is `pub(crate)`.
- Complex modules: Domain, DTO, Row and public Event are separate types; `domain` has no `serde`/`sqlx` derives, and mapping happens at the boundary.
- Thin modules: `domain` holds only structs and simple validation, without Aggregate / Value Object; Rows may double as models, with only DTOs split out.

## 3. Complex and thin modules
A module is **complex**, and uses DDD tactical patterns, if any of these four questions is answered "yes":
1. Is there a rule that must always hold? (e.g. a redemption ID is stored only once; a viewer can check in only once per business day)
2. Are there state transitions, some of them invalid? (e.g. redemption statuses follow Twitch: from `UNFULFILLED` to `FULFILLED` or `CANCELED` (`CANCELED` means the points were refunded); a `CANCELED` one can never become valid again)
3. Would a bug damage data or viewer trust, not just the display?
4. Do other modules depend on these rules, or must the rules apply consistently in several places?

If all four are "no", the module is **thin**: settings CRUD, or turning events into visuals and sound. A thin module becomes complex as soon as its first such rule appears (fill in the domain model); there is no downgrade.

| Module | Type | Reason |
|---|---|---|
| Redemption records | Complex | Deduplication, `UNFULFILLED`/`FULFILLED`/`CANCELED` state transitions, marking records as possibly incomplete |
| Daily check-in | Complex | Once per day, business time zone, three trigger sources, import deduplication |
| Personal badges (a later phase) | Thin | First version is only "viewer/role → badge"; upgrade when rule priorities appear |
| Event alerts | Thin | Queueing, priority and replay are playback logic in the application layer |
| Chat display, sound management, shoutout clips, settings | Thin | CRUD or rendering, no data rules |
| Counters | Thin | Counting and the per-stream reset; "reset only once per stream" rests on the stored session ID, with no other rules |

## 4. Between modules
- **Synchronous queries**: call the other module's public application service trait; never use its internal types.
- **Two kinds of events**:
  - Integration and UI events (chat messages, simulated events, connection status, etc.) are only broadcast in memory; what must be kept as records, a module stores in its own table (e.g. chat logs, activity records).
  - Module domain events (e.g. `RedemptionRecorded`) go through the outbox, and interested modules subscribe to them.
- **Outbox** (built in the check-in slice): when redemption records first stores a record, it publishes `RedemptionRecorded` in the same transaction (event type `redemption.recorded`, with `occurredAt` set to the redemption time).
  - The event and the business data are written in the same transaction.
  - The dispatcher takes events from the outbox in publish order, retries failures and shows them in the UI, and resends after a restart.
  - Delivery state is tracked per subscriber, so one failing subscriber neither re-runs nor blocks the others.
  - Subscribers must be safe to run more than once: processed event IDs go into the subscriber's own inbox table, in the same transaction as the business effect.
  - The outbox table belongs to `core`, which has its own migration folder; writing to the outbox reuses the caller's transaction.
  - The set of subscribers (disabled modules included) is recorded when an event is published; modules added later do not receive past events.
  - Subscribers derive business time (such as the check-in business day) from the event's `occurredAt`, not from processing time, so replayed events never land on the wrong day.
  - Retries are capped (5 attempts in all, 1, 2, 4 and 8 seconds apart; while retrying, the event holds back the later events for that subscriber); past the cap, the event moves to a dead-letter queue shown in the UI with "retry" and "skip" actions, so one event cannot block its subscriber forever.
  - Events delivered to every subscriber are cleaned up every 10 minutes (and once at startup), together with pending deliveries for removed modules.
- Playback results (UI-C5): when a check-in card, a reward sound or reward media is triggered by a Twitch redemption, the module that shows it publishes `RedemptionPlayed` through `Outbox::publish_now` once that item ends (event type `presentation.redemption_played`: the Twitch redemption ID, `what` being `card`, `sound` or `media`, and `result` being the queue's outcome, or `file_missing` when the media file is gone); simulations and tests publish nothing. A failed write is tried again three times with the same event ID (after 1, 5 and 30 seconds), and only then just logged. The outbox can only be built after the modules (it takes their subscriptions), so each module starts with an unconnected `PlayedReporter` that the Host connects once the outbox exists. Redemption records subscribes to the event and keeps it in its own `redemption_playback` (keyed by the outbox event ID, so a redelivery is never kept twice), and announces `redemption.changed` for that record when it first keeps it, so the redemptions page updates; `redemption_records.playback_tracked` is 1 for records added after the column was, 0 for older ones. `GET /api/admin/redemptions` gives each record `played`: what it played and how each ended, in the order they ended; an empty list when it played nothing, `null` for an older record; the redemptions page shows these as the results, 「—」 and 「沒有紀錄」.
- **Disabling modules**:
  - From the skeleton on, modules have an enable/disable switch; while a module is disabled, in-memory events (chat, etc.) are dropped, not kept.
  - When disabling a module that subscribes to the outbox (currently only check-in), the streamer chooses (stored as `disabled_modules` and `closed_modules` in `settings.json`):
    - "Pause": events stay in the outbox undelivered and are delivered in order after re-enabling; retries are not counted while paused; the UI shows the backlog size and the time of the oldest event.
    - "Off": events from the disabled period are marked skipped for that module, with no replay after re-enabling; before choosing, a warning lists the affected events and modules.
    - Switching from "pause" to "off" marks the undelivered events as skipped too.
- **Data**: one SQLite file; each module has its own tables (module prefix) and its own migration folder; **no cross-module joins**: use the public interface to get another module's data. Write transactions always use `BEGIN IMMEDIATE` (or a single writer connection) to avoid SQLite returning `SQLITE_BUSY`; for now only one connection is opened. The database file is `toolkit.db` in the data folder.
- **Migrations**: files use timestamp versions, and `host` merges them into a single Migrator at startup. Rules:
  - Versions must be globally unique and sorted by version after merging; a test checks this.
  - Released migration files must never change (SQLx compares checksums; even a line-ending change breaks startup).
  - Disabled modules must still provide their migrations, or startup fails on missing versions; even if a module is removed, its migration files are kept.
  - The dev command `cargo run -p host --example migrate -- <folder>` applies the merged migrations to that folder's `toolkit.db`, for SQLx offline data (`.sqlx/`).
  - Pre-upgrade backup: when the database already has migrations applied and more are pending, it is first backed up with SQLite's `VACUUM INTO` to `backups/` in the data folder (`toolkit-<UTC time>.db`), never by copying the open file. A newly created database, or one with no new migrations, is not backed up. If the backup fails, nothing is applied: an error is shown and the app exits. Backups are never deleted automatically (they are only made on upgrades).
  - A database with a migration this version does not know (data from a newer version) is refused: an error is shown and the app exits.
- If a dependency cycle appears, move the shared event or type into `core` instead of letting two modules depend on each other.
- External platforms (Twitch, OBS) appear only in `integrations`; business modules never depend on external SDKs and only receive internal events. External values are converted at the integration layer; for example, EventSub redemption statuses are lowercase (`unfulfilled`/`fulfilled`/`canceled`, plus `unknown`) while the Helix API uses uppercase, so both are mapped to internal statuses and `unknown` is handled.

## 5. External communication
- The only clients for now are the admin UI (Tauri window) and OBS overlays, both using HTTP + WebSocket (except the IPC commands listed under "Tauri IPC permissions" below), bound to `127.0.0.1` only. OBS Dock and mobile browser control will be designed later.
- HTTP carries commands and queries; WebSocket pushes events. Every time a client connects to the WebSocket, the first message is a snapshot (the Host subscribes to events before taking the snapshot, to ensure that no events are lost or duplicated during snapshot initialization), and later events follow in increasing `seq`; a reconnect gets a fresh snapshot. The snapshot's `payload` lists, per event type, the recent events kept in memory (for example the last 50 `chat.message` events); `alert` events are not kept, so a reloaded overlay never replays one; as soon as an alert arrives, `alert.received` is also published (likewise not kept), whether or not an alerts overlay in OBS will play it, and the admin window's chat 「事件」 (events) list shows it. Connection status is an event too: only the latest `obs.status` is kept; for OBS's scene and output state, `obs.state`, likewise only the latest is kept. Status contains no secrets, so it goes on the public `/ws/overlay`: the admin UI and overlays get the current status from the snapshot as soon as they connect, and the admin UI can also read it with `GET /api/admin/obs`. When a redemption record is created, changes status or keeps a playback result, `redemption.changed` is published: it carries only the record ID, so viewer text never goes over `/ws/overlay`, and it is not kept in snapshots; on it, or on a new snapshot, the admin UI reads `GET /api/admin/redemptions` again. When a check-in is recorded, `checkin.changed` is published, likewise carrying only the viewer ID and not kept in snapshots; on it, or on a new snapshot, the admin UI reads the check-in data again. Overlay pages connect with `?kind=chat|alerts|checkin|sound|bgm|counter|marathon|break|warnings|leaderboard`, and the Host counts open connections per kind (admin API `GET /api/admin/overlays`) to know whether that overlay has been added to OBS; connections with no kind or one it does not recognize (the admin window, old pages) still connect and count as `other`.
- WebSocket events use a fixed envelope from the first version: `id`, `type`, `version`, `seq`, `occurredAt`, `source`. Internal domain events are never exposed directly; `infrastructure` maps them to public events.
- API contract is code-first: OpenAPI and frontend TS types are generated from Rust, and CI checks that the generated files are up to date.
- **Port**: a fixed default port, `47810`, stored in the data directory's `settings.json`. If it is taken, do not switch ports automatically, so OBS URLs never break silently; the only exception is a data directory's first start (no `settings.json` and no OBS URL yet): if the default port is taken, a free port is picked and saved, and used from then on. The Host is then not running and the settings page cannot open, so the small port-change page opens instead (served directly by Tauri; see "Frontend files" below): it shows the error, lets the user enter and validate a new port, saves it and retries the bind. Its strings also use resource keys.
- **Frontend files**:
  - `apps/web` has three kinds of entries: the admin UI, each overlay, and the small port-change page.
  - The admin UI and overlay build output is embedded into the executable with `rust-embed` and served by the Host.
  - The small port-change page builds into its own folder, which serves as Tauri's `frontendDist` (containing only this page).
  - Tauri sets `app.windows: []`, so the config defines no windows; all windows are created from Rust (in `setup`, or after a successful port retry).
  - "Dev" means the `tauri/custom-protocol` feature is off (`cfg(dev)` / `tauri::is_dev()`), not `debug_assertions`. `tauri build` (including `--debug`) turns it on and is the only distributable build; `tauri dev` and plain cargo commands without this feature (`cargo run`, `cargo build --release`, `cargo test`, `cargo clippy`) are dev. CI turns the feature on manually only for checking and distributes nothing.
  - `cfg(dev)` only applies inside `apps/desktop`: `apps/desktop` decides whether this is dev and passes the extra Vite origin allowed in dev to the Host as runtime configuration; `crates/host` never reads a cfg.
  - `rust-embed` enables the `debug-embed` feature, so debug builds also embed the files into the executable.
  - User-customized HTML/CSS templates (`custom`) live in the data directory's `templates/` folder, put there by the user (see "User templates" under "Local API security" below).
- **Dev mode**: the frontend runs on the Vite dev server with hot reload, proxying `/api`, `/ws`, `/templates`, `/sounds`, `/music`, `/media` and `/checkin` to the Host:
  - The proxy target is `http://127.0.0.1:<port>`, not `localhost` (Node may resolve that to IPv6 `::1`, while the Host binds IPv4 only).
  - `<port>` is read on every request from the dev data folder's `settings.json` (`target\debug\data\` as used by `pnpm tauri dev`, ignoring `--data-dir`; under `CARGO_TARGET_DIR` when set, which must be an absolute path), falling back to the default port when there is no file or its content is invalid: Vite starts before the app, a data folder's first run may switch ports automatically, and the port page may save a new one.
  - The proxy sets `changeOrigin: true` (rewrites only the Host header, not Origin) and `ws: true`.
  - Tauri's `build.devUrl` is set to the Vite URL, so in development both the admin window and the small port-change page are served by Vite and count as a local origin; Vite uses `server.strictPort: true` so the port cannot drift away from the allowlist.
  - Vite sends the same CSP as the Host: pages under `/overlay/` get the overlay CSP and everything else gets the `/admin` CSP (its `frame-src` allows the chat, alert and stamp card overlay pages of the origin in the request's Host header, or `'none'` when the header is not a plain host name and port), so violations show up during development. The middleware in the next item sets it, not `server.headers`: Vite applies that last, which would replace the overlay CSP.
  - In dev mode, Vite allows the `null` origin on every response except the proxied `/api`, `/ws`, `/templates`, `/sounds`, `/music`, `/media` and `/checkin` (`server.cors: false` plus a `configureServer` middleware), because the preview iframe loads modules from paths such as `/@vite/client` and `/src/...`.
  - Sandboxed iframes on any website have the `null` origin, so by the previous item any website can read the files Vite serves. Vite's `server.fs.deny` therefore adds Cargo's `target` folder to the default list: the dev data folder (settings, logs, WebView2 profile) is inside it and must not be readable through Vite.

### Local API security
Binding to `127.0.0.1` does not stop malicious web pages in the browser (cross-site requests, DNS rebinding, WebSocket hijacking), so the following is also required:
- **Admin window**: loads `http://127.0.0.1:<port>/admin` and is created only after the Host has bound the port; in development it loads the Vite dev server instead. The admin window and the API share one origin, so there is no CORS and no Tauri origin to handle. The admin window may only navigate to `/admin` paths on the app's own origin (in dev, the devUrl origin) (`on_navigation` restriction), and opening new windows (`window.open`, `target=_blank`) is always denied (`on_new_window`); the Device Code Flow verification URL is opened in the system browser by a Rust command using `tauri-plugin-opener`, and the window shows only the code. Other external URLs work the same way: each destination gets its own command with a hard-coded URL and no parameters, with no generic command that takes a URL parameter (a script injected into the admin window could use one to open any URL or custom protocol, such as `ms-settings:`), and no window is granted opener plugin permissions.
  - The Host sends a strict `Content-Security-Policy` on `/admin` (and every path under it): `script-src 'self'` (no inline scripts, no eval); `connect-src 'self' ipc: http://ipc.localhost` (Tauri IPC); `style-src 'self' 'unsafe-inline'` (PrimeVue injects styles at runtime, or use PrimeVue's nonce instead); `img-src 'self' data: https://static-cdn.jtvnw.net` and `font-src 'self' data:` (Vite inlines small files as `data:`; viewers' avatars and Twitch badge images in chat load only from Twitch's image CDN, and every URL the Host stores or passes on is checked to be on that domain first); `frame-src` allows only pages under the `/overlay/chat/`, `/overlay/alerts/` and `/overlay/checkin/` paths (the chat, alert and stamp card overlay pages): all three paths on `http://127.0.0.1:<port>` and on `http://localhost:<port>` (for the template previews; `<port>` is the port the Host is currently bound to; CSP path matching ignores the query, so with or without `?preview`; the release IPC capability covers the whole Host origin, so no other same-origin page may be framed inside the admin window). No `default-src`. vue-i18n uses precompiled messages, so `unsafe-eval` is not needed.
- **Admin token**: the Host generates a random token at every launch; it is never written to disk. The admin window fetches it at startup through a Tauri IPC command; the token stays in memory only, never in localStorage (WebView2 writes that to disk). Admin HTTP requests carry an `Authorization` header; admin WebSocket connections send the token in their first message.
- **Tauri IPC permissions**: app commands are declared in `build.rs` with `tauri_build::AppManifest`, and every command needs an explicit grant. There are three capabilities:
  1. Small port-change page (local origin, `port` window only): grants only the commands that validate and save the port and retry the bind.
  2. Admin window, dev (local origin through `devUrl`, `admin` window only): grants admin commands such as fetching the token.
  3. Admin window, release build (the Host URL is a remote origin): created at startup with `Manager::add_capability`, with URLs limited to `http://127.0.0.1:<port>` and the `admin` window only (Tauri matches the IPC request's Origin, which has no path, so it cannot be limited to `/admin`; `on_navigation` restricts the path). The command that opens the new-version download page is granted only here: dev builds do not check for new versions, so they never show the notice. It is not placed in the auto-enabled `capabilities/` folder; keep Tauri's `dynamic-acl` feature (on by default).
  - Commands that open an outside web page never take a URL: the commands that open Twitch's device activation page and the new-version download page take no arguments; the chat log page's 「在 Twitch 開啟」 takes only a Twitch login (lowercase letters, digits and `_`, at most 25 characters), which it puts into the fixed `https://www.twitch.tv/popout/<login>/chat`, and refuses anything else.
  - The 開啟記錄檔資料夾 (open the logs folder, troubleshooting) command takes no arguments and only opens this data folder's `logs/`; the Rust side opens it with the opener, and the page gets no opener or file system permission.
  - Besides app commands, the admin window (capabilities 2 and 3) is granted only `core:event:allow-listen` and `core:event:allow-unlisten` (to receive the close-hint event), never `core:default` or `core:window:*` (the release capability covers the whole Host origin).
- **User templates**:
  - Custom templates and overlays are never rendered directly in the admin window; previews go in an iframe with only `sandbox="allow-scripts"` (no `allow-same-origin`), so template code cannot reach the admin window's IPC or token; a test checks that `invoke` from the preview iframe is rejected.
  - The preview iframe's origin is `null`, so it cannot connect to the Host; the admin window passes the snapshot and the events after it in with `postMessage`.
  - The preview is on the chat full page (`/admin/chat`) and is the chat overlay page with `?preview` (`/overlay/chat/?preview`): it opens no WebSocket and accepts only messages from its parent window whose origin equals the page URL's origin, in the same format as `/ws/overlay`. The admin window first sends a snapshot (the recent chat; when there is none, sample messages marked `source=simulation`), then forwards the other events it receives; when a reconnect brings a new snapshot, or the preview page reloads, it sends a snapshot again. The full page's template picker shows one preview per built-in template (`/overlay/chat/?preview&template=<id>`), and each preview page loads that template from the built-in template route; with `custom` selected, the full page also shows why the folder template cannot be used right now (`GET /api/admin/templates/chat`). The alerts full page (`/admin/alerts`) uses the same picker, with previews at `/overlay/alerts/?preview&template=<id>`: the admin window sends an empty snapshot and one sample alert marked `source=simulation` (a resub with a message); a preview stays silent and replays the latest alert it received over and over, and forwarded alert events take the sample's place.
  - Every response on overlay and template paths (HTML and SVG included) sends the overlay CSP: `script-src 'self'; object-src 'none'`; the template directory serves only non-script file types (allowlist: HTML, CSS, images, fonts, sounds) with `X-Content-Type-Options: nosniff`, enforcing HTML/CSS-only templates in the first version.
  - Selection: the template the chat overlay shows is stored as `chat_template` in `settings.json`, `default` by default. The built-in templates' (`default`, `compact`, `bubble`) sources are in `apps/web/src/overlay/chat/templates/<id>/`, embedded in the executable too, HTML/CSS only. The admin UI switches with `PUT /api/admin/templates/chat` (`{ "selected": "<id>" }`); the Host accepts only `default`, `compact`, `bubble` and `custom` (anything else gets 400 `template.unknown`; a failed save gets 500 `settings.save_failed`), saves, then publishes `template.changed`. `custom` uses the data directory's template instead; the admin UI has no entry for it, so it is set by editing `settings.json` by hand and takes effect after a restart (the Host reads this value only at startup; after picking a built-in template in the admin UI, going back to `custom` takes another edit; the E2E tests switch through the API); an unrecognized value in `settings.json` counts as `default`.
  - Text size: the chat overlay's text size follows the overlay appearance's text size (`--ov-scale`, see "Overlay appearance" below); the template page only picks the template. The former chat text size (`chat_text_size` in `settings.json`, px) is converted once, on the first start after the upgrade: when the template is a built-in one (`default` and `bubble` 24px, `compact` 20px), the size is not the template's own and the appearance text size is still 100 %, the appearance takes the nearest 10 % (50–200 %) of "old size ÷ template size"; an appearance already changed, a size equal to the template's, or the user's template converts nothing. `chat_text_size` is cleared either way, so this runs once; when saving the appearance fails, the old value stays for the next start. The chat overlay may get bigger or smaller, and the user's template does not follow the appearance's text size: both go into the release notes. `PUT /api/admin/templates/chat/text-size` is gone; the `chat.text_size` event (`{ "textSize": <px or null> }`) stays for one release and is always `null` after the upgrade, and the overlay and the previews still set it as the CSS variable `--chat-text-size`.
  - The custom template (`custom`) lives in the data directory's `templates/chat/`: `template.html` (an HTML fragment), `style.css`, plus images, fonts and similar files. The Host never creates or copies this folder; users put it there themselves.
  - Binding: `template.html` must contain one `data-chat-list` element (new messages are appended inside it) and one `<template data-chat-message>` (the markup for one message), in which `data-field="userName"` and `data-field="text"` mark where values go; when the viewer has picked a name color, it is set on each message as the CSS variable `--user-color` (give it a fallback in CSS, e.g. `var(--user-color, #fff)`). The overlay fetches `template.html` with `fetch`, parses it with `DOMParser` (parsing runs no code), removes elements such as `script`, `iframe`, `object`, `embed`, `base` and `meta` and every `on*` attribute. URL attributes (`src`, `href`, `xlink:href`, `poster`, `action`, `formaction`) keep only `http:`, `https:`, `data:` and relative paths, and anything else (such as `javascript:`) is removed; relative paths are pointed into the template directory (paths starting with `/` resolve against the Host root, not the template directory), while same-document fragments starting with `#` (such as SVG `<use href="#icon">`) are left unchanged. Relative paths inside `style` attributes, `<style>` and `srcset` are not rewritten and resolve against the overlay page, so `url()` belongs in `style.css`. The new template is first mounted hidden and replaces the old one only after its stylesheets load (at most 3 seconds), so no unstyled frame flashes. Viewer input is always written with `textContent` and never parsed as HTML.
  - The template route `GET /templates/chat/{*path}` serves the selected template; `GET /templates/built-in/chat/{id}/{*path}` serves any built-in template, for previews (`custom` and unknown IDs get 404). Both serve only allowlisted types, and no path segment may be empty, `.` or `..`, or contain `\` or `:`; for the folder template, after `canonicalize` the file must still be inside the template directory (blocking `..`, symbolic links and junctions); responses also carry `Cache-Control: no-store`. A middleware adds the headers under `/templates`, so error responses produced before the handler runs (bad encoding, wrong method, unknown path, rejected Host header) carry them too.
  - Fallback: when `custom` is selected and `template.html` is missing, cannot be read (including when it is not UTF-8), is larger than 1 MB, or lacks either the `data-chat-list` attribute or a `<template>` tag carrying `data-chat-message` outside HTML comments, the template route serves the built-in default template as a whole, and `GET /api/admin/templates/chat` returns an error code (`template.missing`, `template.unreadable` or `template.invalid`) that the admin UI shows. When the overlay cannot get the template or finds no markers in it, it also uses the default template, so the overlay is never blank.
  - Live apply: every second the Host scans the paths, sizes and modification times of the servable files in the template directory (allowlisted types only, excluding editor temporary files), polling with no extra file-watching dependency; on any change it checks the template again; with `custom` selected it publishes a `template.changed` event on `/ws/overlay` (`source` is `system`; not kept in snapshots), and with a built-in template selected it publishes nothing. Switching templates publishes the same event; `payload.overlay` is `chat` or `alerts`, and each overlay handles only its own. When the overlay receives this event or a new snapshot, it reloads the template, adding a new version parameter to URLs that point into the template directory to bypass caches; current messages are kept and redrawn with the new template; on the alert overlay, the alert playing now finishes its remaining time in the new template.
- **Alert overlay** (`/overlay/alerts/`):
  - Playback: follows, new subs, resubs, gift subs, Bits and raids (from Twitch or the simulator) go into the shared presentation queue (`core`'s `presentation`; alerts and stamp cards share one queue, played one at a time in arrival order, with no limit): after publishing an `alert` event, it waits for that alert's play time (6 seconds; 9 seconds for a resub or cheer with a message) plus 1 second before playing the next item in the queue; when an item's turn comes and no overlay of its kind is connected (see the WebSocket connection counts), it is skipped without waiting, except for items from the simulator (the admin window's preview still needs to receive them); the payload's `durationMs` tells the overlay how long to show it. Each item carries its kind and viewer (`subject`: an alert's kind and viewer, a stamp card's viewer and stamp count, a reward sound's name and the viewer who redeemed it; names are raw text), which home writes as 「特效：阿凱 訂閱了」, 「打卡卡片：小魚 7/10」 and 「音效：喝水（橘子兌換）」. Reward sounds (sound module) and stamp cards (checkin module) do the same, keeping the latest 50 of this launch in memory with their outcomes: recorded when queued (no outcome yet), then with one of the outcomes above when they end; simulated cards count too, marked as simulated. Both use `presentation::Recent` in `core`; each entry carries the record it stands for in its module (a reward sound the Twitch redemption ID, a stamp card the check-in record's ID; simulations none), by which the home page's event feed matches outcomes.

- **Chat commands** (`commands` in `core`, composed by the Host): every feature's chat commands are kept in one table, `chat_commands` in `settings.json`. Each entry maps a command's key to its name, who may use it, the module it belongs to, and what the broadcaster calls it (`label`, e.g. a counter's name); one never saved has its declared default name and is open to everyone. The alerts and checkin modules ask the sound module's public service only when they publish an event, so alerts and check-ins from the simulator play the chosen sound too. While the sound module is disabled, every slot plays its default.

  - Master volume: `PUT /api/admin/sounds/volume` (`{ "volume": 0–100 }`, kept as `sound.volume` in `settings.json`, default 100%; `GET /api/admin/sounds` carries `volume`). When the sound module looks up a slot it multiplies this with the sound's own volume, so reward, alert (the built-in sound included) and check-in sounds all use it, and so does "play in OBS"; it applies even while the sound module is disabled. It is adjusted in the background music player.

- **Background music library** (bgm module): separate from the sound library. Admin API `GET`/`POST /api/admin/music`, `PUT`/`DELETE /api/admin/music/{id}` (`PUT` renames the title).
  - Import and files work as in the sound library: at most 50 MB (larger gets 413 `music.too_large`), and an extension that does not match the magic bytes gets 400 `music.unsupported_type` (both modules share the `audio` check in `core`); the file is copied into the data folder's `music/`, named by a UUID v7. Title, format, length and playlists are kept in `settings.json` under `bgm`. Deleting removes it from `settings.json` (including every playlist) first, then deletes the file.
  - `GET /music/{id}` is the same as `/sounds/{id}`: read-only, no token, only IDs in the music library, `Content-Type` fixed by format, `nosniff`, `no-store`, and no `Access-Control-Allow-Origin`. It also answers a single byte range (206; a malformed range or one outside the file gets 416), so the overlay can start in the middle of a track.
  - Length: the admin window reads it with `<audio>` after import and saves it with `PUT /api/admin/music/{id}/duration` (1 ms to 24 hours); opening the background music page also measures tracks that have no length yet. Each track in `GET /api/admin/music` carries `missing`: `true` when its file is not in `music/` (deleted outside the app), and the page marks it "file missing".
  - Playlists: `POST /api/admin/music/playlists`, `PUT`/`DELETE /api/admin/music/playlists/{id}` (rename, delete; deleting a playlist deletes no tracks). A track can be in several playlists; `PUT /api/admin/music/{id}/playlists` (`{ "playlists": [<playlist ID>] }`) sets which playlists it is in, a newly added track goes to the end of that playlist, and an unknown ID gets 404 `music.not_found` with nothing changed.
  - Player: the Host owns the clock; overlays do not report back. The playing state lives in memory only, so after a restart the player is stopped.
    - Controls: `POST /api/admin/music/player` with `action` `play` (with `playlist`, or the one chosen last when left out; the same playlist resumes when paused, otherwise it starts from the beginning), `pause`, `next`, `previous` (more than 3 seconds in, back to the start of this track; otherwise the track before), `stop` (keeps the chosen playlist) or `seek` (`position_ms`; past the length, the next track starts). No playlist chosen yet gets 400 `music.invalid`; an unknown playlist gets 404 `music.not_found`.
    - Options: `PUT /api/admin/music/player/options` (`volume` 0–100%, `shuffle`), kept as `bgm.volume` (default 50%) and `bgm.shuffle` in `settings.json`.
    - Order: each round's order is decided when it starts (shuffled when shuffle is on); after the last track a new round starts, reshuffled when shuffle is on, and playlist edits take effect from then. Toggling shuffle keeps the track playing and reorders the rest. Tracks whose file is missing, whose length is not measured yet, or that were deleted from the library are skipped; when no track in the playlist can play, `play` gets 409 `music.nothing_to_play`, and a playing player stops.
    - Clock: the position moves on by the measured lengths, and the next track starts when one has played in full. It moves only while playing and while a background music overlay (`/overlay/bgm/`, `?kind=bgm`) is connected; without one the position stands still and is marked `onAir: false`, and the admin UI shows "Overlay not connected" instead of pretending to play. When OBS reloads the source, the clock stands still while it is disconnected and resumes from the same position once it reconnects.
    - The `bgm.player` event, of which the snapshot keeps only the latest: `state` (`stopped`/`playing`/`paused`), `playlist`, `track` (`id`, `title`, `url`, `durationMs`), `positionMs` (the position when published), `onAir`, `shuffle`, `volume`. The overlay works out the current position as `positionMs` plus the time since `occurredAt` (shortcut: assumes the overlay and the Host are on the same computer with the same clock), seeks only when it is more than 1 second off, and pauses while disconnected. The background music page and the home page's background music tile and drawer all show it. In OBS, add this URL as a browser source and tick "Control audio via OBS".
    - 播 5 秒 (play 5 seconds) in the event simulator dialog (`POST /api/admin/music/player/test`, token required) publishes `bgm.test` (`source=simulation`, not kept in snapshots): `track` comes from the playlist chosen last: the first playable track in playlist order; there are also `volume` and `durationMs` (5 seconds). The overlay plays it from the start on a separate audio element, not through the player, and stops when the time is up, when another test arrives, or when a `bgm.player` with `state=playing` arrives, so it never sounds together with real playback. The player's state, track and position do not change. While the feature is off, no playlist has been chosen, the playlist has no playable track, or the music is playing, the Host answers 409 (`music.off`, `music.nothing_to_play`, `music.playing`), and the dialog disables the button first and says why.
  - Scene rules: `PUT /api/admin/music/scene-rules` replaces them all (matched in order; a new rule leaves `id` empty and the Host gives it a UUID v7), kept as `bgm.scene_rules` in `settings.json`; `GET /api/admin/music` carries `scene_rules`. Each rule has a name, scenes (several allowed, trimmed, repeats dropped regardless of case), a playlist, a play mode (`shuffle`), a volume, autoplay on entry (`autoplay`), stop on leaving (`stop_on_leave`) and enabled (`enabled`). An enabled rule must have a playlist, otherwise 400 `music.invalid`; an unknown playlist gets 404 `music.not_found`. Saving does not apply them to the scene on air right away; they take effect at the next scene switch.
    - Switching scenes: the Host follows OBS's scene changes (`StreamingState`), comparing scene names regardless of case. The same scene does nothing. Switching to a scene with no rule (disabled rules and rules without a playlist do not count) always stops. Switching to a rule with autoplay on plays that rule's playlist, with its play mode and volume: a track playing that the new playlist also has plays on uninterrupted, otherwise the playlist starts from the beginning. Switching to a rule with autoplay off looks at the previous scene's rule: if its stop on leaving is on, the music stops; otherwise it keeps playing.
    - When OBS connects, the scene on air is read and applied first (as a switch from no scene); OBS disconnecting counts as switching to a scene with no rule, so the music stops.
    - With no rules at all, scene switches and OBS disconnecting leave the player alone, so those who use no scene rules can still play by hand.
    - Deleting: playlists and tracks in `GET /api/admin/music` carry `used_by` (the names of the scene rules that play it, or whose playlist has it), which the confirmation lists before deleting. Deleting a playlist leaves the rules that used it without a playlist and disables them, and the page shows "Playlist missing"; they are never moved to another playlist. Deleting a track only lists them and disables no rule.
  - Disabling the bgm module hides the background music page and home tile; `play` gets 409 `music.off`, music that is playing stops at the end of the track, and scene switches leave the player alone.
  - Background music has three pages: 「播放」 (`/admin/music`, the player and the scene rules), 「音樂歌單」 (`/admin/music-playlists`) and 「音樂庫」 (`/admin/music-library`), with 「觀眾點播」 grey. When the scene on air has an enabled playlist rule but the background music overlay is not in it, the 「播放」 page warns in its header and offers 「加進場景」, which adds the overlay to the scene on air through the OBS sources' `POST /api/admin/obs/sources` (disabled while OBS is not on this computer).
- **Screen tools** (overlays module. The break card's module ID and page path are both `screen-tools`, so the home tile keeps the ID it had while unbuilt; the warnings (`warnings`) and redemption videos and GIFs (`media`) have switches of their own: with the warnings off the Host sees nothing wrong, so none shows, and with media off only redemption playback stops while the alerts overlay goes on. These switches and the sub marathon's `marathon` were split out of `screen-tools` and `counter`: on the first start after the upgrade each takes the state of the one it came from, "close" included, and `modules_split` in `settings.json` records that the split was done):
  - Break / starting-soon card (`/overlay/break/`, `?kind=break`): stored in `overlays_break_card` (one row: the text, the text after the countdown, the countdown mode `minutes`/`until`, the minutes, the time of day `HH:MM`, whether it is shown, and when the countdown ends). Admin API: `GET`/`PUT /api/admin/screen-tools/break` (text up to 100 characters, minutes 1–1440), `POST /api/admin/screen-tools/break/show` (either `minutes` or `until`; `until` is a UTC time within 24 hours, and the admin window turns "until a time" into the next moment the clock shows it), `POST /api/admin/screen-tools/break/hide`.
  - Showing it stores when the countdown ends, so restarting the toolkit or reloading the overlay shows the same time; every change and every start publishes `screen.break` (the whole card), and the snapshot keeps only the latest one. The overlay counts down by itself, switches to the end text at 0, and the card stays until hidden by hand; the end of the countdown never switches scenes.
  - Warnings (`/overlay/warnings/`, `?kind=warnings`): small text on the stream when something is wrong; viewers see it too. Settings are stored in `overlays_warnings` (one row: three switches, how many seconds the mic may stay muted before a warning, and the name of the OBS audio input to watch); "chat overlay not connected" and "mic muted for more than 30 seconds" are on by default, "Twitch disconnected" is off. Admin API: `GET`/`PUT /api/admin/screen-tools/warnings` (seconds 1–3600).
    - Every 0.5 seconds the Host hands the module what it sees: whether a chat overlay is open (the `?kind=chat` socket count), whether Twitch EventSub is connected, and OBS's audio inputs (unknown while OBS is not connected). The module publishes `screen.warnings` (the settings plus the state) only when the state or the settings change, and the snapshot keeps only the latest one.
    - Mic: picked from OBS's input list (which already lists only inputs with a mute state, that is, inputs with audio); with none picked, nothing is checked. The module records when it first saw the input muted, the overlay shows the warning once the set seconds have passed, and it clears on unmute; picking another input starts the wait again. When OBS is connected but the picked input is not in the list, `micMissing` is set, the warnings page (`/admin/warnings`) asks for a new pick, and the mute is not checked meanwhile.
  - Overlay appearance: the built-in overlays' theme (`dark`, `cream`, `contrast` for high contrast) and text size (50–200 % in steps of 10 %), chosen apart from the admin UI's theme, at the bottom of the OBS sources page; the text size covers the chat overlay too. Stored in `overlays_appearance` (one row); admin API `GET`/`PUT /api/admin/screen-tools/appearance`; every change and every start publishes `screen.appearance`, the snapshot keeps only the latest one, and open overlays change at once without a reload.
    - How it applies: on receiving it, an overlay page sets CSS variables on its root (`--ov-fg` text, `--ov-bg` background, `--ov-accent` accent, `--ov-shadow` text shadow, `--ov-scale` text scale); dark at 100 % sets none, which is the built-in overlays' own look. The built-in overlays (break card, warnings, counters, marathon timer, stamp card, leaderboard) and the built-in chat and alert templates read these variables with their own values as the fallback; custom templates do not read them, so they stay as written. A Host test checks that every built-in template's CSS reads the theme and the text scale.
    - Built-in overlays added later must also call `followAppearance` from `apps/web/src/overlay/appearance.ts` and read the same variables.
  - Media library (videos and GIFs shown on redemptions): admin API `GET`/`POST /api/admin/screen-tools/media`, `PUT`/`DELETE /api/admin/screen-tools/media/{id}` (`PUT` changes the title and length). The list is stored in `overlays_media` (UUID v7, title, format, length); the files are `media/<id>.<format>` in the data folder and are backed up and restored with the rest.
    - Import: the body is the file itself and `?name=` carries the original file name (only its extension and a starting title are taken from it; it is never used as a path); only GIF, WebM and MP4 are accepted, at most 50 MB (larger gets 413 `media.too_large`), and an extension that does not match the magic bytes (`GIF87a`/`GIF89a` for GIF, the EBML header for WebM, `ftyp` for MP4) gets 400 `media.unsupported_type`.
    - Length: a GIF starts at 5 seconds and can be changed (1 ms to 10 minutes); the admin window reads a video's length with `<video>` after import and saves it, and opening the 「影片與 GIF」 page (`/admin/media`) also reads videos that have no length yet.
    - `GET /media/{id}` works like `/music/{id}`: read-only, no token, only IDs in the library, a fixed `Content-Type` per format, `nosniff` and `no-store`; byte ranges are not supported yet (short clips played from the start do not need them).
  - Video or GIF on a redemption (set on 兌換時播放): each channel points reward (listed as in the check-in settings) maps to at most one media library item, stored in `overlays_media_rules` (reward ID, item, position `top_left`/`top_right`/`bottom_left`/`bottom_right`/`center`/`full`, and volume; a `null` volume follows the sound master volume). Admin API: `GET /api/admin/screen-tools/media-rules`, `PUT`/`DELETE /api/admin/screen-tools/media-rules/{reward_id}`, `POST /api/admin/screen-tools/media-rules/{reward_id}/test` (試播, test play). Deleting a media item deletes the rules that use it.
    - Playing: where the Host hands a redemption to the sound module, it also hands it to this module. A new redemption (not a status update, and not while the module is off) with a rule queues on the presentation queue (`Stage::Alerts`, queue item `media`) and plays on the alerts overlay, so no extra source is needed; when its turn comes the module publishes `screen.media` (URL, format, position, volume, length; not kept in snapshots), and the alerts overlay shows the GIF or video at its position, the video with its sound; a skip or the emergency stop takes it away at once. A video whose length has not been read yet is not queued.
    - When the file is gone, the item is declined by the module when its turn comes (it takes no time and holds up nothing behind it); the module records why, and the event feed says "file missing". The rules and the library are kept in memory, so a redemption queues in the same step it arrives; redemptions from before a restart never play late.
    - 試播 publishes `screen.media` with `source=simulation` directly, without the presentation queue, and records nothing.
- **Host header**: accept only `127.0.0.1:<port>` and `localhost:<port>`, to block DNS rebinding.
- **Origin**: every WebSocket connection (overlays included) and every state-changing request checks Origin, accepting only `http://127.0.0.1:<port>` and `http://localhost:<port>` (current port); dev mode also accepts the Vite dev server origin (passed in by `apps/desktop` as runtime configuration). WebSocket connections without an Origin or with `Origin: null` are always rejected.
- **CORS**: none on `/api`, `/ws` and `/admin`. Only the build `assets/` directory (chunks shared by the admin UI and overlays) and the template paths (`/templates`, built-in templates included) send `Access-Control-Allow-Origin: *` (without credentials; the content is public code and templates), because the preview iframe's origin is `null` and Vite's module scripts, CSS and fonts must load through CORS.
- **Overlays**: routes are read-only, can only read snapshots and subscribe to public events, and have no state-changing endpoints; OBS URLs contain no token.
- **OBS Dock**: not done for now; its pairing will be designed later together with mobile remote control.

### Twitch rate limits
Twitch's official documentation is the source for these numbers; update this section when Twitch changes them.
- **Helix API** uses Twitch’s points bucket per client ID and user. All Helix calls share the same handling. A 401 refreshes the token and retries once. When the bucket reaches zero or a 429 has a `Ratelimit-Reset` header, new calls for that account pause until the reset, for at most a minute. Callers handle a 429 without a reset time using their own backoff. A Helix or OAuth request that receives no response within 15 seconds is treated as unreachable.
- **EventSub WebSocket**: per user token (client ID and user), at most 3 connections with enabled subscriptions, at most 300 subscriptions per connection, and a `max_total_cost` of 10. The app opens only 1 connection per account and closes the old one before changing the Client ID or signing out; on `session_reconnect` it moves to the reconnect URL Twitch sends (this is not a new connection; subscriptions carry over and are not created again); failed connections reconnect with exponential backoff (from 1 second, at most 60 seconds).
- **Live state and stream sessions** (stream module): subscribes to `stream.online` and `stream.offline` (no authorization needed; each costs 1 of the `max_total_cost`), and only a start whose `type` is `live` counts; while signed in it also checks with Helix Get Streams every 60 seconds (once right after signing in), which picks up a stream that started before the app started or while EventSub was disconnected, and updates the viewer count. Each Twitch stream is one session, stored in `stream_sessions` (the Twitch stream ID is the unique key, so receiving the same stream twice counts as one session; the start time is Twitch's); after the stream ends, that session remains the current one until the next stream starts; opening a new session ends any other session not yet ended (a missed `stream.offline`, e.g. the app was closed during the stream and reopened during the next one) at the new stream's start time. Signing out of Twitch makes the state `unknown` and leaves the sessions as they are (signing out does not prove the stream ended). Get Streams lags behind the events by about a minute, so: when a check still lists the stream already ended by `stream.offline`, no session is reopened; a stream that started before the current session (a late check or event) is always ignored, and an older session never ends one that started later; when a check says there is no stream, only a session that started more than 3 minutes ago counts as ended (making up for a missed `stream.offline`). The state is published as the `stream.status` event (`state` is `unknown`/`offline`/`live`; while live it also carries `startedAt` and `viewers`), and snapshots keep only the latest one; the admin UI's top bar shows 「直播中」 (live), the duration and the viewer count, or 「已下播」 (ended), from it. Each session also stores its peak viewer count (the larger value at each check while live), kept across restarts.
- **This stream's stats** (composed by the Host): `GET /api/admin/stream/summary` returns the latest session (the live one, or after it ends the last one until the next starts) with its start and end times, peak viewers, and the follows, subs (new subs and resubs, each sub a gift hands out included), bits, raids and redemptions in it; `null` before the first session. Each module counts in its own table (activity records by session ID, redemption records by the session's time range), with no join across modules; `endedSinceLaunch` says the session ended after this launch. The stage switch at the top of home (left of 「編輯首頁」) switches by itself from `stream.status` and this summary: 直播中 while live; 下播後 for a stream that ended after this launch; 開播前 otherwise (after a restart, signed out, or no Twitch stream). The broadcaster can switch to another stage to look at it until the state next changes; a stage picked by hand shows 「手動選的」 and 「改回自動」 beside it. Tiles go by their feature's name (such as 場景與模式 and 休息卡片) while their IDs stay; the break card tile's big text is 「顯示中」 or 「收起」. Each stage has its own home order, and 「編輯首頁」 edits the stage picked now (the stage can be switched while editing). The orders are stored in `settings.json`: 直播中 in `home_tiles` (the only one before), 開播前 and 下播後 in `home_tiles_before` and `home_tiles_after`; `GET`/`PUT /api/admin/home-tiles?stage=before|live|after` (default `live`) reads or writes one, with the same checks, and `null` means not arranged yet, so that stage's defaults show. The defaults: 開播前 has 「開播前檢查」 with the scene, background music, sound, alert and chat tiles; 直播中 has 「待處理」 (shown only with items: an overlay with two or more sources in OBS, or the scene on air having a playlist rule while the background music overlay is not in it; each opens the OBS sources page and goes away once its cause does), 「本場直播」 (the numbers while live; normally a small tile with the time, redemptions and subs), the event feed, 「呈現佇列」 (normally a small tile with how many wait and what plays) and every feature tile; 下播後 has 「本場摘要」 (with export) with the counter, redemption, check-in and chat tiles. An order saved before counts as the 直播中 one, and the first time the Host reads it, it gets 待處理, 本場直播 and 呈現佇列 first (`home_tiles_version`). While live, the numbers are read again every 30 seconds. 開播前 lists the pre-stream checks with 「N / M 好了」, unfolded by default to all of them; folded, only the heading row with the count is left, whether or not some are not ready: Twitch signed in, EventSub connected (`eventsub_connected` of `GET /api/admin/twitch`: `true` once the current EventSub connection has subscribed, `false` when the connection ends or on logout; reports from the previous connection after a sign-in change do not count), OBS connected, and the overlay of each enabled feature connected in OBS (the counter and marathon timer overlays only show numbers on screen, which is optional, so they are not listed; `GET /api/admin/overlays`, read every 3 seconds while 開播前 is shown); a Twitch, EventSub or OBS item that is not ready has 「修正」, which leads to the connections section of settings; an overlay that is not in OBS yet has the OBS status link right on its item, which opens the OBS sources page to add it to a scene. An overlay not in OBS yet counts as a warning (yellow); any other item that is not ready is a problem (red). Later features add their own checks. The 下播後 summary has 「匯出本場紀錄」: `GET /api/admin/stream/record` returns the latest stream's follows, subs and resubs (each sub a gift hands out on its own row, the gift itself not listed), cheers, raids and redemptions, one row each, as the stream stats count them (simulated events are never stored, so none are here); the admin UI saves them as CSV (time, kind of event, viewer, amount or content), UTF-8 with a BOM, CRLF lines, every cell quoted, and a cell starting with `=`, `+`, `-`, `@`, Tab, CR or a line feed gets a leading `'` so spreadsheets never read it as a formula. Saving works like the backup export: it first asks where (`showSaveFilePicker`), and downloads instead without that API.
- **Event feed** (composed by the Host): `GET /api/admin/feed` lists, newest first, the latest 50 alerts, redemptions and check-ins of this stream (the latest session, from its start; before any session, since this launch): who, what they did, what it set off (an alert, a reward sound with its name, a stamp card, a reward video or GIF with its name; a reward with both a sound and a video lists the sound) and what became of that (queued, played, played without its missing sound file, overlay not open so not played, declined by its module (with the reason when the Host knows it; for now only "file missing"), skipped, dropped by 清空排隊, emergency stop). The activity, redemption and checkin modules each answer for their own table by time range (`activity_between`, `redeemed_between`, `checked_in_between`), and the subs a gift hands out, stored one by one, are not listed separately; the outcomes come from the alerts, sound, checkin and overlays modules' in-memory recent lists, so only this launch has them, and after a restart older events show without them. Simulated events are never written to database tables, so they come only from the in-memory alerts and stamp cards, marked 「測試」. The home page's 「事件流」 tile (no module's, always shown) shows the count and the latest item, and a click opens it on home into the whole list; the small tiles of 本場直播, 事件流 and 呈現佇列 open in place into a block (本場直播 a whole row, 事件流 about two thirds, the queue about a third), and 「收合」 on the block turns it back, with focus kept in place; what is open lasts for this window only and is never saved. it reads again, at most once a second, when a live message may have changed it.
- **Rehearsal** (composed by the Host, `/rehearsal`): a script is JSON (`{"steps": [{"type": "chat" | "alert" | "checkin" | "stop", "at": <ms>, …}]}`, at most 256 KB, 1000 steps, each within 30 minutes); the built-in scripts (多人打卡 crowd check-ins, 揪團湧入 raid rush, 開場高峰 opening peak, 測試緊急停止 emergency stop test) are sent by the admin UI in the same format; their stamps fit the current card slots, and the last card is full. `POST /api/admin/simulate/script` (`speed`: `normal`, `double`, or `burst` for all at once) plays it on a timeline in the Host, every step through the simulator (chat reaches the chat display only, alerts the alerts overlay only, stamp cards record nothing, and `stop` is the emergency stop), so it is always `source=simulation`, a `source` written in the file is ignored, and nothing reaches any real record, statistic or counter. Broken JSON is reported with its line; an unknown step or a missing field with the step's number. One script plays at a time; a new script or `POST /api/admin/simulate/script/stop` stops the one playing.
- **Leaderboard** (composed by the Host, `/leaderboard`, overlay `/overlay/leaderboard/?board=…&period=…`, `?kind=leaderboard`): bits, gifted subs (the gift's own count), chat messages and check-ins, top 10 each; the periods are this stream (the latest session, or since this launch before any), this month (by the check-in time zone and reset hour, from the start of the month's first business day) and all (whatever the record retention kept; the check-in "all" is the check-in page's total, imported baselines included). The activity, chat and checkin modules each rank their own records by time range (`ranking`, `top_chatters`, `top_checkins`) and the Host only composes them, with no join across modules; simulated events are never stored, and common chat bots are left out by the Host's list (`GET /api/admin/chat/bots`, which the chat log's 隱藏機器人 uses too). Admin API `GET /api/admin/leaderboard`; the Host works the boards out again every 30 seconds and publishes `leaderboard.update` (every board and period) only when they change, and the snapshot keeps only the latest one. The overlay follows the overlay appearance.
- **Troubleshooting** (Settings › 問題排解, composed by the Host): `GET /api/admin/diagnostics/connections` (when signed in, one Helix `GET /eventsub/subscriptions` call measures the latency and reads the subscription count, plus whether EventSub and OBS are connected), `GET /api/admin/diagnostics/logs?level=` (the newest 200 lines in the logs folder, by level, with error code and message, shown on this page only) and `GET /api/admin/diagnostics/report` (the diagnostic report: version, connection state, modules turned off, and the latest warnings and errors with time, level and error code only). A row that is not connected or not signed in carries 「去設定」 (go to settings), which links to that part (Twitch or OBS) of the connections page in settings. The report may be posted publicly, so it holds no token, password, webhook URL, chat, viewer name or ID, nor any log message text.
  - Performance: the Host samples every 2 seconds (`GET /api/admin/performance`): this computer's CPU and memory, this app's process CPU and memory (`sysinfo`), and, through the streaming-software port, OBS's CPU (`GetStats`), its render and stream dropped frames and the bytes the stream sent (`GetStreamStatus`). The dropped-frame share and the bitrate come from the counter differences over the last 60 seconds; above 5 % the troubleshooting page warns at the top. While OBS is not connected its numbers show "—" and the rest work as usual; when OBS restarts (its counters go down) the window starts again.
- **Preview output device** (Settings › 一般 › 音訊, admin window only): sound and music previews in the admin UI play on the chosen device through `HTMLMediaElement.setSinkId`; what OBS plays follows OBS. The choice is this window's preference, kept in `localStorage` (device ID and name, no secret). When the device is unplugged or setting it fails, the system default plays. Device names need the microphone permission: it is asked once, only when 顯示裝置名稱 (show device names) is pressed, and the microphone is stopped as soon as the list is read, never kept.
- **Image sizes** (Host composition, `/image-sizes`): `POST /api/admin/image-sizes?kind=badge|points&fit=pad|crop|manual` (`manual` also takes `crop_x`, `crop_y` and `crop_side` in the picture's pixels; missing or outside the picture gets 400 `image_sizes.invalid_crop`), whose body is the picture itself (PNG, JPEG, GIF or WebP; at most 10 MB and 4096 px a side, otherwise 413 `image_sizes.too_large`; other formats or broken files get 400 `image_sizes.unsupported`). The picture is first squared by transparent edges, by cropping the middle or by cropping the square picked (on the page a square frame is dragged over the picture and resized by its corner, arrows move it and Shift with arrows resizes it, the rest is dimmed, a new picture puts the frame back in the middle at its largest, and the picture shows as a `data:` URL), then resized to PNGs for subscriber badges (72/36/18 px) or channel points icons (112/56/28 px), optimized losslessly. A badge above 25 KB is reduced to 256 colors, kept only when that is smaller; one still above is flagged `too_large` and shown in red. The response gives each size's byte count and a `data:` preview (the admin window's CSP `img-src` has no `blob:`); with `zip=true` it is one zip instead, saved through the save dialog. Everything stays on this computer: nothing is stored or uploaded.
- **Activity records** (activity module): each follow, sub, resub, gift (including each sub it hands out), cheer and raid from Twitch is stored as one row in `activity_events`, with the session ID at the moment the event arrived (the stream module answers in arrival order, so an event right after a stream start always counts toward the new session; no join across modules); the EventSub message ID is the unique key, so a redelivered notification is stored once; simulated events are not stored. The record retention is stored in `settings.json` as `record_retention` (`{"days": N}` with N from 1 to 3650, or `"forever"`; when unset it is 30 days, shared with chat logs), and records past it are deleted at start and once a day; when `settings.json` cannot be read or holds an invalid value, nothing is deleted that time, rather than guessing from the default. Admin API: `GET`/`PUT /api/admin/records/retention` (`PUT` deletes the records the new retention no longer keeps in one database transaction, commits it only after `settings.json` is saved, and returns how many it deleted; if saving fails, the delete is cancelled too; after an error the admin UI reads the retention actually in effect again) and `GET /api/admin/records/expired?days=N` (how many records changing to N days would delete); before shortening the retention, settings 「資料與備份」 shows how many records will be deleted and asks to confirm. The records are in the database, so they are exported and restored with backups. Other modules' record tables (currently the chat log) are handed to the activity module as `core`'s `RecordTable` and deleted and counted with each module's own SQL: the daily clean-up, the single transaction when the retention changes, and "how many would be deleted" all include them, and the activity module never touches another module's table.
- **Chat log** (chat module): chat messages from Twitch (simulated ones are not stored; none are taken while the chat module is disabled) are stored in `chat_messages`, with the session ID at the moment the message arrived (asked the same way as for activity records), with the Twitch message ID as the unique key; the `payload` column holds the `chat.message` payload. Writes run in the background in arrival order, in batches (at most 200 messages each). When a moderator deletes a message, or clears a viewer or the whole chat (`channel.chat.message_delete`, `channel.chat.clear_user_messages`, `channel.chat.clear`), the stored messages have their text and fragments emptied and are marked deleted, rather than the row being removed; clearing a viewer or the whole chat reaches back only 24 hours; at the same time `chat.removed` is published (`messageId`, `userId`; when neither is present, it means the whole chat) and those messages are taken out of the snapshot, so the chat overlay removes them and the admin window's chat shows 「這則訊息已被管理員刪除」 instead. `GET /api/admin/chat/messages` returns the latest 200 messages (deleted markers included), which the admin window puts ahead of the live messages when it opens, so earlier chat is still visible after a restart; the chat overlay in OBS still takes only the snapshot, so old messages do not appear there after a restart. This stream's stats also carry the session's chat message count (`chatMessages`). Chat messages and viewer updates are written in separate batches of up to 200 items or 75 milliseconds. Moderation jobs flush preceding chat messages first and wait for queue space when necessary. Tray quit and app-initiated restart wait for accepted chat writes to finish. Older records with an unknown channel can still be cleared by message ID.
- **Chat display in the admin UI**: the `chat.message` payload also carries each of Twitch's own badges (`twitchBadges`: `setId`, `id`, `info`, in Twitch's order; `badges` are still the roles), and during a shared chat a message from another channel carries `sharedFrom` (that channel; this channel's own messages and chat outside a shared chat have none). `GET /api/admin/chat/badges` returns Twitch's global badges and the broadcaster channel's badges (Helix Get Global/Channel Chat Badges, no scope needed), read once per launch and kept in memory, keeping only those whose image is on Twitch's CDN; while signed out or when they cannot be read it returns an empty list, so chat shows no badge images. `GET /api/admin/viewers/avatars?ids=` returns the avatars the viewers module has stored (at most 200 viewers at a time); a new viewer's avatar is looked up in the background, so when the admin UI finds none it asks again a little later, at most three times. The chat display settings (style compact/standard/comfortable, avatars, badges, time, text size 80–150%) are stored in `settings.json` as `chat_display`, through `GET`/`PUT /api/admin/chat-display`, shared by the chat log page and the docked chat. During a shared chat both show 「共享聊天中」 and the other channels at the top (learned from the messages received), with a 「只看本頻道」 toggle. The OBS chat overlay templates are unchanged.
- **First chat**: EventSub has no mark for "a viewer's first message in this channel", so while signed in a second Twitch IRC connection is opened (`wss://irc-ws.chat.twitch.tv:443`, anonymous and read-only as a `justinfan` guest, needing no sign-in or scope; it sends only `CAP REQ :twitch.tv/tags twitch.tv/commands`, `NICK`, `JOIN #<broadcaster login>` and replies to `PING`, and the login's format is checked first). It reads the `first-msg=1` tag on `PRIVMSG` and matches its `id` to EventSub's message ID (Twitch's Delete Chat Messages documentation says the message ID is the IRC `id` tag, and EventSub's message ID is used with the same API; not yet confirmed with a real message, and a mark that matches nothing is not shown). The connection starts with EventSub after sign-in and ends on logout, reconnecting with the same exponential backoff on disconnects; its state is `irc_connected` in `GET /api/admin/twitch`, and the Twitch section of settings shows which way first chats are decided. While IRC is not connected, the viewers module decides instead: a message from a viewer the toolkit sees for the first time counts as a first chat (which is not the same as their first in the channel). A mark may arrive before or after its message: one that arrives early is kept (at most 200) and the message carries `firstChat: true` when it arrives; one that arrives late publishes `chat.first` (`messageId`) and updates that message in the snapshot. Stored messages record it in the `first_chat` column of `chat_messages`; this stream's stats also carry the session's first-chat count (`firstChats`), the chat log page gains a 「第一次聊天」 filter, and chat marks the message 「第一次聊天」.
- IRC first-chat detection starts only after both capabilities are acknowledged and the channel join succeeds. Bulk moderation applies to the receiving broadcaster and the preceding 24 hours. Bulk clears keep the text of older messages that have no broadcaster ID. The admin UI reconciles recent deletions and first-chat marks when reconnecting. Failed chat writes are retried in arrival order with a delay capped at 30 seconds while the Host is running. The worker holds at most 200 operations plus 2,048 waiting, including 64 slots reserved for deletions. While full, new writes beyond capacity are refused. Live chat continues and both admin chat views show the number of missed writes for this launch.
- **Chat log page** (composed by the Host): `GET /api/admin/chat/periods` lists, newest first, the latest 50 streams (from start to end) and the chat between two streams (before the first and after the last one ended count too; gaps without chat are left out), each with its message count and the time of its first message; the page labels them 「11/16 的直播」 or 「11/15（沒有直播）」. `GET /api/admin/chat/log?from=&to=` returns the messages stored for that time (at most the latest 5000, marked `truncated` when there are more) and the activity and redemption records (at most 2000 of each; the subs a gift hands out are not listed separately, the gift entry stands for them), each module reading its own table, interleaved by time. 「即時」 is the admin window's live messages (the latest 200 loaded first) plus the alerts received since the page opened. The filters (全部, 提到我, !指令, 管理員和 VIP, 訂閱者, 醒目訊息和小奇點, 兌換, 訂閱揪團和追隨), search and 「隱藏機器人」 (a built-in list of common bots) work together, all in the admin UI. On reconnect, the admin window reloads the selected period and applies the snapshot’s deletion events to the query results. If the live chat history cannot be loaded, the window shows a notice and retries automatically. The history page also applies first-chat marks from the reconnect snapshot. On an offline message whose period is missing from the selector, the page retries the period lookup after a short delay.
- **Viewer directory** (viewers module): one row per Twitch user seen in chat, alerts or redemptions, stored in `viewers` (the Twitch user ID is the primary key, so a renamed user updates the same row): login, display name, avatar, the roles shown by their chat badges the last time they chatted (broadcaster, moderator, VIP, subscriber; only chat carries badges, so other events do not change roles), and when they were first and last seen. Viewers without avatars are looked up on Twitch (Helix Get Users) in groups of up to 100, with up to two retries on temporary failure, and only `https://static-cdn.jtvnw.net/` URLs are stored (sharing the check and the lookup interface in `core` with check-ins). Simulated events never create or change viewers; check-ins' own viewer data is not moved over. Other modules get names only through the public lookups (`search`, `names`, `avatars`) and never read this table.
  - Each connection subscribes to 14 events: `channel.chat.message`; `channel.follow` (v2), `channel.subscribe`, `channel.subscription.message`, `channel.subscription.gift`, `channel.cheer` and `channel.raid` (with the `to_broadcaster_user_id` condition) for alerts; `channel.channel_points_custom_reward_redemption.add` and `.update` for redemption records; `stream.online` and `stream.offline` for the stream state; `channel.chat.message_delete`, `channel.chat.clear_user_messages` and `channel.chat.clear` for the chat log (with the same condition and scope `user:read:chat` as `channel.chat.message`). Raids and the stream state need no authorization by the broadcaster and cost 1 each; the others are authorized by the broadcaster and cost 0, 3 in total, well under 10.
  - When a sign-in from before an update lacks the scope an event needs, that event is not subscribed; when Twitch answers a subscription other than chat with an error status (including 429, or a channel without channel points), only a warning is logged and chat and the other events carry on. Only a failed chat subscription, or any subscription that encounters an invalid sign-in or cannot reach Twitch, counts as a failed connection and reconnects.
- **Device Code Flow**: poll at the `interval` Twitch returns until `expires_in`, never faster, and at least 1 second apart.
- **Sending chat messages**: nothing sends chat messages yet. When sending is added later (for example check-in replies), messages must be queued and rate-limited locally, using the conservative value of 20 messages per 30 seconds. Twitch allows 20 messages per 30 seconds for regular accounts and 100 per 30 seconds for the broadcaster, moderators and VIPs (messages from the broadcaster still count toward the 20-message bucket); going over makes Twitch ignore the account's messages for 1 hour.

### OBS connection
- `obws` connects to obs-websocket 5, which is built into OBS, without TLS. The address is stored in `settings.json` as `obs.host`/`obs.port` (default `127.0.0.1`/`4455`); the password is stored in the Windows Credential Manager, wrapped in a `SecretString` as soon as it is read, and never written to `settings.json` or logs; with no password set, the app connects without authentication (a normal state when OBS has authentication turned off). The handshake sends only the challenge response, never the password itself.
- Streaming-software interface: the state of scenes, items, inputs and outputs is defined in `core`'s `streaming` (`StreamingState` and the `StreamingSoftware` trait), and OBS is just one implementation of it; the scenes page and later features such as modes go only through this interface, never using `obws` directly. The commands so far are switching the scene, showing or hiding an item, locking an item, reordering an item, placing an item, turning studio mode on or off, setting the preview scene, transitioning, creating a browser source, adding an existing source to a scene, and removing an item; they go out over the same connection the state uses. Their result is not taken from the command's response: it shows up in the state once OBS's event arrives. Other commands, such as muting, are added when a feature needs them.
- After connecting, it first reads the full state once (the current scene; each scene's items, whether they are shown, whether they are locked and their source kind, with items ordered front to back as in OBS's source list; whether each input that can be muted is muted (an input without audio, such as an image or a display capture, which OBS answers does not support audio, is left out and does not end the connection); whether OBS is streaming and recording, studio mode, the preview scene, the transitions and the one in use), then updates it from OBS events: scene switches, item visibility and locking, mute, streaming and recording state, the preview scene and the transition are updated in place, and turning studio mode on reads everything again; when scenes, items or inputs are added, removed, renamed or reordered, it reads everything again. Items inside groups are not listed. On disconnect the state is cleared (the scene is `null`, meaning unknown) and read again after reconnecting. The state is published as the `obs.state` event, whose `payload` is the whole state; the admin UI's top bar shows 「串流中」 (streaming) and 「錄影中」 (recording) from it.
- When the connection fails or drops, it reconnects with exponential backoff (from 1 second, at most 60 seconds, the same as EventSub); after a successful connection the backoff starts again from 1 second. Each connection attempt (including the handshake and version check) takes at most 10 seconds.
- Status (event `obs.status`; its `payload` holds `state` and `reason`; `reason` is a stable code, and `null` when `connected` or right after startup):
  - `connected`: connected.
  - `reconnecting`: not connected yet, or a state that recovers on its own, for example OBS is not running (`obs.unreachable`), OBS was closed (`obs.disconnected`), or the connection opened but the handshake failed or did not finish in time (`obs.handshake_failed`, for example when the other side is not obs-websocket). OBS not running is a normal state, not an error.
  - `error`: still retrying, but the user has to fix something, for example a wrong password (`obs.auth_failed`), OBS requires a password but none is set (`obs.password_required`), or an unsupported version (`obs.unsupported_version`; OBS 30.2 or later and obs-websocket 5.x at 5.5 or later are required).
- Logs record only status changes, so OBS staying closed for a long time does not keep writing logs.
- Admin API `/api/admin/obs`:
  - `GET` returns the address, whether a password is set (`password_set`; the password itself is never returned) and the current status; if the Credential Manager cannot be read, it returns 500 `obs.secret_store_failed`.
  - `PUT` changes the address and password (an omitted `password` keeps the stored one, an empty string deletes it) and reconnects with the new settings right away, clearing the old connection's scene and output state; the replaced connection no longer writes any state. The host accepts only host names and IPv4 addresses, and the port must not be 0; otherwise it returns 400 `obs.invalid_address`.
  - `PUT` saves `settings.json` before writing the password: if writing the password fails, the new address still takes effect and it returns 500 `obs.secret_store_failed`; if `settings.json` cannot be saved, it returns 500 `settings.save_failed` and the address, password and connection all stay as they were.
- Admin API `PUT /api/admin/obs/scene` (switches the scene, `scene`) and `PUT /api/admin/obs/item` (`scene`, `item`, plus at least one of `enabled`, `locked`, `position` (the place counted front to back, 0 being the front, turned into OBS's bottom-up index) and `placement` (`x` and `y` in canvas pixels, `align` one of nine points; scale, rotation and crop stay); with none it returns 400 `obs.nothing_to_change`): returns 204 on success; 409 `obs.not_connected` when OBS is not connected; 404 `obs.not_found` when the current state or OBS has no such scene or item; 502 `obs.request_failed` when OBS refuses or the connection drops while sending. The scene page belongs to the module `scene`; turning it off only hides its page and home tile; each row of its item table moves the item forward or back and shows and changes its position (`GET /api/admin/obs/placements?scene=…` returns the canvas size, which is OBS's base resolution, and each item's `x`, `y` and `align`), with a note when the position is off the canvas, and an item whose source is a duplicated overlay (two or more sources with the same overlay address) is marked 「重複」, linking to the OBS sources page; 「加入 Overlay」 under the table lists the built-in overlays not in the scene yet with their suggested sizes and adds the one picked through `POST /api/admin/obs/sources` (disabled, with a note, while OBS is not on this computer).
- Studio mode: the state carries `studioMode`, `preview` (the scene in the preview while studio mode is on, `null` otherwise), `transitions` and `transition` (the one in use). `PUT /api/admin/obs/studio` (`enabled`) turns studio mode on or off; `PUT /api/admin/obs/preview` (`scene`) sets the preview scene; `POST /api/admin/obs/transition` (`transition` optional, the one in use when left out; one not in `transitions` returns 404 `obs.not_found`) puts the preview on air. Turning studio mode on or off, changing the preview or the transition in OBS shows in the state too. While studio mode is on, picking a scene on the scene page only sets the preview, and the page notes that an overlay test still shows on stream when its source is in both the preview and the scene on air.
- OBS sources page (`/obs-sources`): `GET /api/admin/obs/sources` lists the browser sources that show one of this Host's overlays (`GetInputList` by kind finds the browser sources, `GetInputSettings` reads each one's `url`): the source's name, the overlay's path and query, and the scenes it is an item of (items inside a group do not count), plus the scene on air and every scene; while OBS is not connected `connected` is `false` and the rest is empty, and a failed read returns 502 `obs.request_failed`. Addresses are compared only inside the Host: an address is this toolkit's when it is `http`, its host is `127.0.0.1` or `localhost`, its port is the Host's current port and its path starts with `/overlay/`; the addresses of other browser sources may hold another service's token, so they are never returned or logged. Two or more sources with the same overlay address are a duplicate; one source in several scenes is not. Suggested sizes and what each overlay shows live in the admin UI. The pre-stream checks still decide whether an overlay is in OBS from its WebSocket connections (it counts once it has really loaded); the OBS sources page reads OBS's scene setup.
- `POST /api/admin/obs/sources` (`scene`, `overlay`, `name`, `width`, `height`) puts an overlay in a scene: when a browser source already shows it, that source gets a new item in the scene; otherwise a new browser source opens `http://127.0.0.1:<port>` plus the overlay path (never with a token), named "name 2", "name 3" when the name is taken. `DELETE /api/admin/obs/sources?scene=…&overlay=…` removes only that scene's items whose source shows the overlay, and the source stays in the other scenes; with no such item it returns 404 `obs.not_found`. Adding and removing match sources as the admin UI does: an overlay with a query (a leaderboard's board and period) must match exactly, one without is matched by its path only. While OBS is not on this computer (the saved host is not `127.0.0.1` or `localhost`), adding returns 409 `obs.not_local` and `local` in the `GET` is `false`; invalid data returns 400 `obs.invalid_source`; other errors are as above.

## 6. Host lifecycle
The Host runs in the Tauri process. Closing the admin window only hides it to the system tray and overlays keep running; closing the small port-change page also keeps the app in the tray; only Quit in the tray stops the Host.

When ✕ is clicked on the admin window, Rust always calls `prevent_close()`: if "Don't show again" is already stored in `settings.json`, the window is hidden right away; otherwise Rust sends an event to the admin window to show a hint, and the frontend reports "shown", "cancel" or "hide" with the app command `close_hint`; "hide" also carries the "Don't show again" checkbox value, which Rust writes to `settings.json`. If "shown" does not arrive within 2 seconds, or ✕ is clicked again while the hint is open, the window is hidden directly so that ✕ never appears to do nothing. "Ask before closing the window" under Settings → General changes the same value (admin API `GET`/`PUT /api/admin/general`; `ask_before_close` is the opposite of "Don't show again"); Rust rereads `settings.json` on every ✕, so a change applies immediately.

### Data directory
Each data directory is a separate app instance, identified by its `instance-id`: settings, logs, cache and WebView2 data all live in it. The app ships as a portable package only, so data defaults to the `data` folder next to the executable.
- Which data directory is used: the one given by `--data-dir <path>` on the command line; otherwise the `data` folder next to the executable (dev builds too, so theirs is `target\debug\data\`).
- Contents: `settings.json`, `logs/` (JSON, rotated daily, kept 14 days), `cache/`, `templates/` (`custom` chat templates, which users put there; stamp card animation packs, which the Host creates when importing them), `sounds/` (imported sounds), `music/` (imported background music), `media/` (videos and GIFs shown on redemptions), `checkin/` (stamp card style images), `WebView2/`, `instance-id`, `toolkit.db` (the database), `backups/` (backups taken before upgrades and restores); a restore also uses the temporary `restore-staging/`, `restore-pending` and `restore-previous/` (see "Backup files" below).
- Only one instance may run per data directory; different data directories can run side by side (for example to test a new version). `instance-id` is a random ID inside the data directory and survives moving it; a copied data directory keeps the same `instance-id`, counts as the same instance and cannot run next to the original. A new `instance-id` is made only when the file does not exist (`create_new`, so two copies starting together get the same ID); any other read error is shown and the app exits instead of switching to a new ID.
- Twitch sign-in and the OBS password are per data directory: the Credential Manager entries are named `<instance-id>/twitch` and `<instance-id>/obs`.
- If the data directory is not writable, show an error and exit; never fall back to another location.
- Side-by-side copies: extract the package more than once, or point `--data-dir` at different directories. There is no installer (see "Distribution" in decisions.en.md).

Backup files (`.stbackup`, "Backup and restore" on the settings page):
- A zip file holding the data (`settings.json` and the database `toolkit.db`), the media (`templates/`, `sounds/`, `music/`, `media/`, `checkin/`) or both, plus `manifest.json`; never `logs/`, `cache/`, `WebView2/`, `backups/` or `instance-id`. Twitch sign-in and the OBS password live in the Credential Manager, not in the data directory, so they never go into a backup; the Client ID is not a secret and is backed up with `settings.json`.
- The database is first saved as a snapshot in `cache/` with `VACUUM INTO`, then added to the zip; the open file is never read directly. Exporting during a stream leaves chat, alerts and check-ins running; database writes wait only while the snapshot is taken.
- `manifest.json`: `format` (`streamer-toolkit-backup`), `format_version` (1 when it holds both kinds, which older versions read too; 2 when it holds one, which older versions refuse with `backup.newer_version` rather than take for a whole backup), `contents` (`data`, `media`: the kinds it holds; a version 1 manifest without it holds both), `app_version`, `schema_version` (the newest migration applied to the database, 0 for an empty one), `created_at` (UTC, RFC 3339), `records` (`redemptions`, `checkins`: how many redemption and check-in records there are), `files` (each file's `path`, `size` and `sha256`).
- Paths may only be `settings.json`, `toolkit.db`, or relative paths under `templates/`, `sounds/`, `music/`, `media/` or `checkin/`, separated by `/`; no segment may be empty, `.` or `..`, contain `\`, `:` or other characters Windows does not allow, or be a reserved name (`CON`, `NUL` and so on). Symbolic links and junctions are not backed up.
- Limits: 20 GB in total once extracted and 100,000 files (the backup file itself may be at most 1 GB more, room for zip headers and data that does not compress). Export and restore (including the automatic `before-restore` backup) use the same limits: going over is refused as a whole (413 `backup.too_large`; the admin UI lists the limits), and no file is ever skipped, so every exported file can be restored.
- Disk space: an export needs free space of the size of what it holds; a restore upload needs twice the backup file's size free (the uploaded file plus the extracted staging). Without it, 507 `backup.no_space` (with `needed`, in bytes) answers before anything is written, and the admin UI says how much space is needed. Free space is read with `GetDiskFreeSpaceExW`; when it cannot be read nothing is refused, and running out mid-write still fails as a whole, leaving nothing half-written.
- Export: the admin API `GET /api/admin/backup` returns the backup file; `?contents=data` or `?contents=media` exports one kind only, both otherwise. The export offers all, data only or media only, each with its current size (`GET /api/admin/backup/sizes`); once saved, it shows the name of the saved file. When checking, every path must belong to a kind listed in `contents`, and `toolkit.db` is required exactly when the data is; version 1 must hold both. The admin UI first opens a save dialog (`showSaveFilePicker`) to choose where, then writes the response there; without that API the browser downloads the file instead.
- A restore replaces only the kinds the backup holds and leaves the rest; each kind is still replaced as a whole, never merged. After a data-only restore, media the data points to but that is missing shows as missing, as it already does. The preview lists the kinds it holds:
  1. Choosing a file: the admin UI uploads it in parts, showing 上傳中 1.2 / 3.4 GB (uploading) and 檢查中 (checking), and can cancel. `POST /api/admin/backup/restore/upload` (body `{ size }`) first checks the limits and the disk space, answers a one-time upload ID and creates `cache/restore-upload-<ID>.part`; there is one upload at a time, and starting another drops the earlier one. `PUT /api/admin/backup/restore/upload/{id}?offset=` adds one part (8 MB from the admin UI; the Host takes at most 16 MB per request); `offset` must equal the bytes received so far (otherwise 409 `backup.upload_offset` with `received`), and nothing past the size given at the start is accepted; a failed write drops the whole upload. `DELETE /api/admin/backup/restore/upload/{id}` cancels; a wrong ID (cancelled, replaced or never started) answers 404 `backup.upload_gone`. Once everything has arrived, `POST /api/admin/backup/restore/upload/{id}/check` checks the file and stages it, and removes the uploaded file whatever the result. A `restore-upload-*` left by a cancel, a cut-off upload or the app ending mid-way is removed at the next start, before the database opens. The checks read the file in 64 KB pieces, so memory use does not grow with the backup's size. Before anything is written, it is checked: the limits, every path, each file's size and SHA-256 (reading at most one byte more than the manifest says; the zip's own size fields are never trusted), and that the zip holds exactly the listed files plus the manifest. A `format_version` or `schema_version` newer than this version answers 400 `backup.newer_version`; any other mismatch answers 400 `backup.invalid`. Once it passes, it is extracted to the data directory's `restore-staging/`; then the database itself is checked (every applied migration must be one this version knows, with the same checksum and finished; an unknown one also answers `backup.newer_version`) and `settings.json` must parse. Only then is `manifest.json` written, marking the staging complete, and a preview returned (backup time, app version, redemption and check-in record counts, number of template folders, number of sound files, number of background music files). Any failing step deletes `restore-staging/`; the data in use is never touched.
  2. Confirming: `POST /api/admin/backup/restore` (409 `backup.nothing_staged` when nothing is staged) writes `restore-pending` (holding a new ID for this restore), answers 202, then restarts the app (`AppHandle::request_restart`, keeping the command-line arguments).
  3. At startup (see "Startup order"): the current data of the kinds about to be replaced is first saved as `backups/before-restore-<UTC time>.stbackup` (which can be restored the same way later); then the current items of those kinds (data: `settings.json` and the database with `-wal` and `-shm`; media: `templates/`, `sounds/`, `music/`, `media/` and `checkin/`) move into `restore-previous/` (which first gets `.contents`, so putting back touches only those kinds) and the staged ones move into place (renames inside the data directory; before anything moves, `restore-previous/` gets the same restore ID); then the normal database open runs (backing up first when migrations are pending). If any step fails, the contents of `restore-previous/` go back into place, the reason is shown and startup continues; on success a notice says the backup holds no Twitch sign-in or OBS password, so sign in again and re-enter it when needed. Finally `restore-pending`, `restore-previous/` and `restore-staging/` are deleted; the restore ID and the staged `manifest.json` go first, so if `restore-pending` cannot be deleted (the error is shown and the user is asked to delete it by hand), the next start neither puts old data back nor applies the restore again.
  - If the app ends in the middle of the moves, the next start finds both `restore-pending` and `restore-previous/` with the same restore ID, puts the original data back first and explains that the restore was interrupted. A `restore-previous/` with another ID (or none) was left by an earlier restore that had finished, and its data was backed up to `backups/` then: it is never put back, and is deleted before the new restore is applied. If even that fails, both are kept, the error is shown and the app exits; the next start tries again.
  - Staged but never confirmed: the next start just deletes `restore-staging/`.
  - `instance-id` is not in the backup and does not change on restore; the Credential Manager entries are named after it, so restoring into another data directory or another PC means signing in to Twitch and entering the OBS password again.
- A backup is a snapshot of when it was exported: chat that a moderator deletes after the export keeps its text in that backup; restoring that backup brings the text back, and deletions are not kept across a restore.

Startup order:
1. Resolve the data directory and check that it is writable. `tauri-plugin-single-instance` names its lock after the identifier, so at startup the identifier gets the `instance-id` appended and the lock is per data directory. Register this plugin first, so a second copy never tries to take the port before handing off.
2. Apply a confirmed restore first (see "Backup files"), then open the database and apply migrations; both come after the single-instance lock, so a second copy never touches the same data directory.
3. The Host binds the port; on failure, open the small port-change page and retry after the user saves.
4. Release build: create the remote capability for the current port, then create the admin window and load the Host URL. Dev mode: the admin window loads the Vite dev server and uses capability 2.
5. Before creating any window, check that the WebView2 Runtime is present (built into Windows 11; missing on a few Windows 10 PCs). If it is missing, show an explanation and open Microsoft's download page; the Host, overlays and tray keep running, and after installing it, choosing Open in the tray creates the window without a restart.

## 7. Enforcing the rules
- Cross-module dependencies: enforced by each crate's `Cargo.toml`.
- Layer rules: architecture tests (`crates/arch-tests`) run in CI. They check that `domain/` contains no occurrence of `sqlx`/`axum` at all (including `use`, derives and full paths), that code in `application/` (outside comments and tests) never uses `infrastructure` (publishing and other adapters are injected by infrastructure as callbacks), and use `cargo metadata` to check dependency direction: modules may depend only on `core` and other modules, never on `integrations` or `host`; `core` depends on no other workspace crate; `integrations` depends only on `core`; only `integrations` may depend on external platform SDKs (`obws`, `tokio-tungstenite`). Module internals are always `pub(crate)`, so other modules see only each other's public interfaces; Cargo itself forbids dependency cycles, and when one appears the shared types move to `core`.
