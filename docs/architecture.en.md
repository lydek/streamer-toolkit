# Architecture

DDD + Clean Architecture, implemented as a Modular Monolith: one program, one crate per business module, layers inside each module. Adopted progressively: DDD tactical patterns are used only in complex modules. Tech choices and adoption timing are in [decisions.en.md](decisions.en.md).

## 1. Layout
Update this section when the layout changes.

```text
crates/
  core/            # Shared core (package name `toolkit-core`, avoiding Rust's built-in `core`): settings, module registry and enable/disable controls, internal integration events, event envelope, in-memory event broadcast, outbox (with its own migrations)
  integrations/    # Twitch (EventSub) and OBS (obws) adapters: turn external events into internal events; handle OAuth, reconnect, backoff, rate limits
  modules/
    chat/          # Chat display (thin)
    alerts/        # Event alerts: follows, subs, Bits, raids (thin)
    redemption/    # Redemption records (complex)
    checkin/       # Daily check-in (complex): subscribes to RedemptionRecorded and chat command events
    sound/         # Sound management (thin)
    stream/        # Live state and stream sessions (thin)
    activity/      # Activity records: follows, subs, Bits, raids (thin)
    viewers/       # Viewer directory (thin)
  host/            # Composition root: wires modules, Axum HTTP/WebSocket routes, overlay static pages
  arch-tests/      # Architecture tests only (see §7)
apps/
  desktop/         # Tauri 2 shell: starts the Host in-process, system tray, single-instance lock; the admin window loads the Host URL
  web/             # Vue 3 + TS: admin UI, overlay pages, small port-change page
```

## 2. Layers inside a module
Every module crate has three layer folders, thin modules included, so an upgrade needs no file moves.

| Layer | Contents | May depend on |
|---|---|---|
| `domain/` | Entities and rules; complex modules use Aggregate / Value Object / Domain Event | Only shared types from `core`; **must not** use `sqlx` or `axum` |
| `application/` | Use cases and ports (Repository traits, public service traits) | `domain` |
| `infrastructure/` | `db/`: SQLx Repository implementations and Rows; `http/`: Axum handlers and DTOs (OpenAPI generated); event mapping | `application`, `domain` |

- A module's `lib.rs` exposes only application service traits, public DTOs and public events; everything else is `pub(crate)`.
- Complex modules: Domain, DTO, Row and public Event are separate types; `domain` has no `serde`/`sqlx` derives, and mapping happens at the boundary.
- Thin modules: `domain` holds only structs and simple validation, without Aggregate / Value Object; Rows may double as models, with only DTOs split out.

## 3. Complex and thin modules
A module is **complex**, and uses DDD tactical patterns, if any of these four questions is answered "yes":
1. Is there a rule that must always hold? (e.g. a redemption ID is stored only once; a viewer can check in only once per business day)
2. Are there state transitions, some of them invalid? (e.g. redemption statuses follow Twitch: from `UNFULFILLED` to `FULFILLED` or `CANCELED` (`CANCELED` means the points were refunded); a `CANCELED` one can never become valid again)
3. Would a bug damage data or viewer trust, not just the display?
4. Do other modules depend on these rules, or must the rules apply consistently in several places?

If all four are "no", the module is **thin**: settings CRUD, or turning events into visuals and sound. A thin module becomes complex as soon as its first such rule appears (fill in the domain model); there is no downgrade.

| Module | Type | Reason |
|---|---|---|
| Redemption records | Complex | Deduplication, `UNFULFILLED`/`FULFILLED`/`CANCELED` state transitions, marking records as possibly incomplete |
| Daily check-in | Complex | Once per day, business time zone, three trigger sources, import deduplication |
| Personal badges (a later phase) | Thin | First version is only "viewer/role → badge"; upgrade when rule priorities appear |
| Event alerts | Thin | Queueing, priority and replay are playback logic in the application layer |
| Chat display, sound management, shoutout clips, settings | Thin | CRUD or rendering, no data rules |

## 4. Between modules
- **Synchronous queries**: call the other module's public application service trait; never use its internal types.
- **Two kinds of events**:
  - Integration and UI events (chat messages, simulated events, connection status, etc.) are only broadcast in memory and never written to the database.
  - Module domain events (e.g. `RedemptionRecorded`) go through the outbox, and interested modules subscribe to them.
- **Outbox** (built in the check-in slice): when redemption records first stores a record, it publishes `RedemptionRecorded` in the same transaction (event type `redemption.recorded`, with `occurredAt` set to the redemption time).
  - The event and the business data are written in the same transaction.
  - The dispatcher takes events from the outbox in publish order, retries failures and shows them in the UI, and resends after a restart.
  - Delivery state is tracked per subscriber, so one failing subscriber neither re-runs nor blocks the others.
  - Subscribers must be safe to run more than once: processed event IDs go into the subscriber's own inbox table, in the same transaction as the business effect.
  - The outbox table belongs to `core`, which has its own migration folder; writing to the outbox reuses the caller's transaction.
  - The set of subscribers (disabled modules included) is recorded when an event is published; modules added later do not receive past events.
  - Subscribers derive business time (such as the check-in business day) from the event's `occurredAt`, not from processing time, so replayed events never land on the wrong day.
  - Retries are capped (5 attempts in all, 1, 2, 4 and 8 seconds apart; while retrying, the event holds back the later events for that subscriber); past the cap, the event moves to a dead-letter queue shown in the UI with "retry" and "skip" actions, so one event cannot block its subscriber forever.
  - Events delivered to every subscriber are cleaned up every 10 minutes (and once at startup), together with pending deliveries for removed modules.
- **Disabling modules**:
  - From the skeleton on, modules have an enable/disable switch; while a module is disabled, in-memory events (chat, etc.) are dropped, not kept.
  - When disabling a module that subscribes to the outbox (currently only check-in), the streamer chooses (stored as `disabled_modules` and `closed_modules` in `settings.json`):
    - "Pause": events stay in the outbox undelivered and are delivered in order after re-enabling; retries are not counted while paused; the UI shows the backlog size and the time of the oldest event.
    - "Off": events from the disabled period are marked skipped for that module, with no replay after re-enabling; before choosing, a warning lists the affected events and modules.
    - Switching from "pause" to "off" marks the undelivered events as skipped too.
- **Data**: one SQLite file; each module has its own tables (module prefix) and its own migration folder; **no cross-module joins**: use the public interface to get another module's data. Write transactions always use `BEGIN IMMEDIATE` (or a single writer connection) to avoid SQLite returning `SQLITE_BUSY`; for now only one connection is opened. The database file is `toolkit.db` in the data folder.
- **Migrations**: files use timestamp versions, and `host` merges them into a single Migrator at startup. Rules:
  - Versions must be globally unique and sorted by version after merging; a test checks this.
  - Released migration files must never change (SQLx compares checksums; even a line-ending change breaks startup).
  - Disabled modules must still provide their migrations, or startup fails on missing versions; even if a module is removed, its migration files are kept.
  - The dev command `cargo run -p host --example migrate -- <folder>` applies the merged migrations to that folder's `toolkit.db`, for SQLx offline data (`.sqlx/`).
  - Pre-upgrade backup: when the database already has migrations applied and more are pending, it is first backed up with SQLite's `VACUUM INTO` to `backups/` in the data folder (`toolkit-<UTC time>.db`), never by copying the open file. A newly created database, or one with no new migrations, is not backed up. If the backup fails, nothing is applied: an error is shown and the app exits. Backups are never deleted automatically (they are only made on upgrades).
  - A database with a migration this version does not know (data from a newer version) is refused: an error is shown and the app exits.
- If a dependency cycle appears, move the shared event or type into `core` instead of letting two modules depend on each other.
- External platforms (Twitch, OBS) appear only in `integrations`; business modules never depend on external SDKs and only receive internal events. External values are converted at the integration layer; for example, EventSub redemption statuses are lowercase (`unfulfilled`/`fulfilled`/`canceled`, plus `unknown`) while the Helix API uses uppercase, so both are mapped to internal statuses and `unknown` is handled.

## 5. External communication
- The only clients for now are the admin UI (Tauri window) and OBS overlays, both using HTTP + WebSocket (except the IPC commands listed under "Tauri IPC permissions" below), bound to `127.0.0.1` only. OBS Dock and mobile browser control will be designed later.
- HTTP carries commands and queries; WebSocket pushes events. Every time a client connects to the WebSocket, the first message is a snapshot (the Host subscribes to events before taking the snapshot, to ensure that no events are lost or duplicated during snapshot initialization), and later events follow in increasing `seq`; a reconnect gets a fresh snapshot. The snapshot's `payload` lists, per event type, the recent events kept in memory (for example the last 50 `chat.message` events); `alert` events are not kept, so a reloaded overlay never replays one; as soon as an alert arrives, `alert.received` is also published (likewise not kept), whether or not an alerts overlay in OBS will play it, and the admin window's chat 「事件」 (events) list shows it. Connection status is an event too: only the latest `obs.status` is kept; for OBS's scene and output state, `obs.state`, likewise only the latest is kept. Status contains no secrets, so it goes on the public `/ws/overlay`: the admin UI and overlays get the current status from the snapshot as soon as they connect, and the admin UI can also read it with `GET /api/admin/obs`. When a redemption record is created or changes status, `redemption.changed` is published: it carries only the record ID, so viewer text never goes over `/ws/overlay`, and it is not kept in snapshots; on it, or on a new snapshot, the admin UI reads `GET /api/admin/redemptions` again. When a check-in is recorded, `checkin.changed` is published, likewise carrying only the viewer ID and not kept in snapshots; on it, or on a new snapshot, the admin UI reads the check-in data again. Overlay pages connect with `?kind=chat|alerts|checkin|sound`, and the Host counts open connections per kind (admin API `GET /api/admin/overlays`) to know whether that overlay has been added to OBS; connections with no kind or one it does not recognize (the admin window, old pages) still connect and count as `other`.
- WebSocket events use a fixed envelope from the first version: `id`, `type`, `version`, `seq`, `occurredAt`, `source`. Internal domain events are never exposed directly; `infrastructure` maps them to public events.
- API contract is code-first: OpenAPI and frontend TS types are generated from Rust, and CI checks that the generated files are up to date.
- **Port**: a fixed default port, `47810`, stored in the data directory's `settings.json`. If it is taken, do not switch ports automatically, so OBS URLs never break silently; the only exception is a data directory's first start (no `settings.json` and no OBS URL yet): if the default port is taken, a free port is picked and saved, and used from then on. The Host is then not running and the settings page cannot open, so the small port-change page opens instead (served directly by Tauri; see "Frontend files" below): it shows the error, lets the user enter and validate a new port, saves it and retries the bind. Its strings also use resource keys.
- **Frontend files**:
  - `apps/web` has three kinds of entries: the admin UI, each overlay, and the small port-change page.
  - The admin UI and overlay build output is embedded into the executable with `rust-embed` and served by the Host.
  - The small port-change page builds into its own folder, which serves as Tauri's `frontendDist` (containing only this page).
  - Tauri sets `app.windows: []`, so the config defines no windows; all windows are created from Rust (in `setup`, or after a successful port retry).
  - "Dev" means the `tauri/custom-protocol` feature is off (`cfg(dev)` / `tauri::is_dev()`), not `debug_assertions`. `tauri build` (including `--debug`) turns it on and is the only distributable build; `tauri dev` and plain cargo commands without this feature (`cargo run`, `cargo build --release`, `cargo test`, `cargo clippy`) are dev. CI turns the feature on manually only for checking and distributes nothing.
  - `cfg(dev)` only applies inside `apps/desktop`: `apps/desktop` decides whether this is dev and passes the extra Vite origin allowed in dev to the Host as runtime configuration; `crates/host` never reads a cfg.
  - `rust-embed` enables the `debug-embed` feature, so debug builds also embed the files into the executable.
  - User-customized HTML/CSS templates (`custom`) live in the data directory's `templates/` folder, put there by the user (see "User templates" under "Local API security" below).
- **Dev mode**: the frontend runs on the Vite dev server with hot reload, proxying `/api`, `/ws`, `/templates` and `/sounds` to the Host:
  - The proxy target is `http://127.0.0.1:<port>`, not `localhost` (Node may resolve that to IPv6 `::1`, while the Host binds IPv4 only).
  - `<port>` is read on every request from the dev data folder's `settings.json` (`target\debug\data\` as used by `pnpm tauri dev`, ignoring `--data-dir`; under `CARGO_TARGET_DIR` when set, which must be an absolute path), falling back to the default port when there is no file or its content is invalid: Vite starts before the app, a data folder's first run may switch ports automatically, and the port page may save a new one.
  - The proxy sets `changeOrigin: true` (rewrites only the Host header, not Origin) and `ws: true`.
  - Tauri's `build.devUrl` is set to the Vite URL, so in development both the admin window and the small port-change page are served by Vite and count as a local origin; Vite uses `server.strictPort: true` so the port cannot drift away from the allowlist.
  - Vite sends the same CSP as the Host: pages under `/overlay/` get the overlay CSP and everything else gets the `/admin` CSP (its `frame-src` allows the chat and alert overlay pages of the origin in the request's Host header, or `'none'` when the header is not a plain host name and port), so violations show up during development. The middleware in the next item sets it, not `server.headers`: Vite applies that last, which would replace the overlay CSP.
  - In dev mode, Vite allows the `null` origin on every response except the proxied `/api`, `/ws`, `/templates` and `/sounds` (`server.cors: false` plus a `configureServer` middleware), because the preview iframe loads modules from paths such as `/@vite/client` and `/src/...`.
  - Sandboxed iframes on any website have the `null` origin, so by the previous item any website can read the files Vite serves. Vite's `server.fs.deny` therefore adds Cargo's `target` folder to the default list: the dev data folder (settings, logs, WebView2 profile) is inside it and must not be readable through Vite.

### Local API security
Binding to `127.0.0.1` does not stop malicious web pages in the browser (cross-site requests, DNS rebinding, WebSocket hijacking), so the following is also required:
- **Admin window**: loads `http://127.0.0.1:<port>/admin` and is created only after the Host has bound the port; in development it loads the Vite dev server instead. The admin window and the API share one origin, so there is no CORS and no Tauri origin to handle. The admin window may only navigate to `/admin` paths on the app's own origin (in dev, the devUrl origin) (`on_navigation` restriction), and opening new windows (`window.open`, `target=_blank`) is always denied (`on_new_window`); the Device Code Flow verification URL is opened in the system browser by a Rust command using `tauri-plugin-opener`, and the window shows only the code. Other external URLs work the same way: each destination gets its own command with a hard-coded URL and no parameters, with no generic command that takes a URL parameter (a script injected into the admin window could use one to open any URL or custom protocol, such as `ms-settings:`), and no window is granted opener plugin permissions.
  - The Host sends a strict `Content-Security-Policy` on `/admin` (and every path under it): `script-src 'self'` (no inline scripts, no eval); `connect-src 'self' ipc: http://ipc.localhost` (Tauri IPC); `style-src 'self' 'unsafe-inline'` (PrimeVue injects styles at runtime, or use PrimeVue's nonce instead); `img-src 'self' data:` and `font-src 'self' data:` (Vite inlines small files as `data:`); `frame-src` allows only pages under the `/overlay/chat/` and `/overlay/alerts/` paths (the chat and alert overlay pages): both paths on `http://127.0.0.1:<port>` and on `http://localhost:<port>` (for the template previews; `<port>` is the port the Host is currently bound to; CSP path matching ignores the query, so with or without `?preview`; the release IPC capability covers the whole Host origin, so no other same-origin page may be framed inside the admin window). No `default-src`. vue-i18n uses precompiled messages, so `unsafe-eval` is not needed.
- **Admin token**: the Host generates a random token at every launch; it is never written to disk. The admin window fetches it at startup through a Tauri IPC command; the token stays in memory only, never in localStorage (WebView2 writes that to disk). Admin HTTP requests carry an `Authorization` header; admin WebSocket connections send the token in their first message.
- **Tauri IPC permissions**: app commands are declared in `build.rs` with `tauri_build::AppManifest`, and every command needs an explicit grant. There are three capabilities:
  1. Small port-change page (local origin, `port` window only): grants only the commands that validate and save the port and retry the bind.
  2. Admin window, dev (local origin through `devUrl`, `admin` window only): grants admin commands such as fetching the token.
  3. Admin window, release build (the Host URL is a remote origin): created at startup with `Manager::add_capability`, with URLs limited to `http://127.0.0.1:<port>` and the `admin` window only (Tauri matches the IPC request's Origin, which has no path, so it cannot be limited to `/admin`; `on_navigation` restricts the path). The command that opens the new-version download page is granted only here: dev builds do not check for new versions, so they never show the notice. It is not placed in the auto-enabled `capabilities/` folder; keep Tauri's `dynamic-acl` feature (on by default).
  - Besides app commands, the admin window (capabilities 2 and 3) is granted only `core:event:allow-listen` and `core:event:allow-unlisten` (to receive the close-hint event), never `core:default` or `core:window:*` (the release capability covers the whole Host origin).
- **User templates**:
  - Custom templates and overlays are never rendered directly in the admin window; previews go in an iframe with only `sandbox="allow-scripts"` (no `allow-same-origin`), so template code cannot reach the admin window's IPC or token; a test checks that `invoke` from the preview iframe is rejected.
  - The preview iframe's origin is `null`, so it cannot connect to the Host; the admin window passes the snapshot and the events after it in with `postMessage`.
  - The preview is on the chat full page (`/admin/chat`) and is the chat overlay page with `?preview` (`/overlay/chat/?preview`): it opens no WebSocket and accepts only messages from its parent window whose origin equals the page URL's origin, in the same format as `/ws/overlay`. The admin window first sends a snapshot (the recent chat; when there is none, sample messages marked `source=simulation`), then forwards the other events it receives; when a reconnect brings a new snapshot, or the preview page reloads, it sends a snapshot again. The full page's template picker shows one preview per built-in template (`/overlay/chat/?preview&template=<id>`), and each preview page loads that template from the built-in template route; with `custom` selected, the full page also shows why the folder template cannot be used right now (`GET /api/admin/templates/chat`). The alerts full page (`/admin/alerts`) uses the same picker, with previews at `/overlay/alerts/?preview&template=<id>`: the admin window sends an empty snapshot and one sample alert marked `source=simulation` (a resub with a message); a preview stays silent and replays the latest alert it received over and over, and forwarded alert events take the sample's place.
  - Every response on overlay and template paths (HTML and SVG included) sends the overlay CSP: `script-src 'self'; object-src 'none'`; the template directory serves only non-script file types (allowlist: HTML, CSS, images, fonts, sounds) with `X-Content-Type-Options: nosniff`, enforcing HTML/CSS-only templates in the first version.
  - Selection: the template the chat overlay shows is stored as `chat_template` in `settings.json`, `default` by default. The built-in templates' (`default`, `compact`, `bubble`) sources are in `apps/web/src/overlay/chat/templates/<id>/`, embedded in the executable too, HTML/CSS only. The admin UI switches with `PUT /api/admin/templates/chat` (`{ "selected": "<id>" }`); the Host accepts only `default`, `compact`, `bubble` and `custom` (anything else gets 400 `template.unknown`; a failed save gets 500 `settings.save_failed`), saves, then publishes `template.changed`. `custom` uses the data directory's template instead; the admin UI has no entry for it, so it is set by editing `settings.json` by hand and takes effect after a restart (the Host reads this value only at startup; after picking a built-in template in the admin UI, going back to `custom` takes another edit; the E2E tests switch through the API); an unrecognized value in `settings.json` counts as `default`.
  - The custom template (`custom`) lives in the data directory's `templates/chat/`: `template.html` (an HTML fragment), `style.css`, plus images, fonts and similar files. The Host never creates or copies this folder; users put it there themselves.
  - Binding: `template.html` must contain one `data-chat-list` element (new messages are appended inside it) and one `<template data-chat-message>` (the markup for one message), in which `data-field="userName"` and `data-field="text"` mark where values go; when the viewer has picked a name color, it is set on each message as the CSS variable `--user-color` (give it a fallback in CSS, e.g. `var(--user-color, #fff)`). The overlay fetches `template.html` with `fetch`, parses it with `DOMParser` (parsing runs no code), removes elements such as `script`, `iframe`, `object`, `embed`, `base` and `meta` and every `on*` attribute. URL attributes (`src`, `href`, `xlink:href`, `poster`, `action`, `formaction`) keep only `http:`, `https:`, `data:` and relative paths, and anything else (such as `javascript:`) is removed; relative paths are pointed into the template directory (paths starting with `/` resolve against the Host root, not the template directory), while same-document fragments starting with `#` (such as SVG `<use href="#icon">`) are left unchanged. Relative paths inside `style` attributes, `<style>` and `srcset` are not rewritten and resolve against the overlay page, so `url()` belongs in `style.css`. The new template is first mounted hidden and replaces the old one only after its stylesheets load (at most 3 seconds), so no unstyled frame flashes. Viewer input is always written with `textContent` and never parsed as HTML.
  - The template route `GET /templates/chat/{*path}` serves the selected template; `GET /templates/built-in/chat/{id}/{*path}` serves any built-in template, for previews (`custom` and unknown IDs get 404). Both serve only allowlisted types, and no path segment may be empty, `.` or `..`, or contain `\` or `:`; for the folder template, after `canonicalize` the file must still be inside the template directory (blocking `..`, symbolic links and junctions); responses also carry `Cache-Control: no-store`. A middleware adds the headers under `/templates`, so error responses produced before the handler runs (bad encoding, wrong method, unknown path, rejected Host header) carry them too.
  - Fallback: when `custom` is selected and `template.html` is missing, cannot be read (including when it is not UTF-8), is larger than 1 MB, or lacks either the `data-chat-list` attribute or a `<template>` tag carrying `data-chat-message` outside HTML comments, the template route serves the built-in default template as a whole, and `GET /api/admin/templates/chat` returns an error code (`template.missing`, `template.unreadable` or `template.invalid`) that the admin UI shows. When the overlay cannot get the template or finds no markers in it, it also uses the default template, so the overlay is never blank.
  - Live apply: every second the Host scans the paths, sizes and modification times of the servable files in the template directory (allowlisted types only, excluding editor temporary files), polling with no extra file-watching dependency; on any change it checks the template again; with `custom` selected it publishes a `template.changed` event on `/ws/overlay` (`source` is `system`; not kept in snapshots), and with a built-in template selected it publishes nothing. Switching templates publishes the same event; `payload.overlay` is `chat` or `alerts`, and each overlay handles only its own. When the overlay receives this event or a new snapshot, it reloads the template, adding a new version parameter to URLs that point into the template directory to bypass caches; current messages are kept and redrawn with the new template; on the alert overlay, the alert playing now finishes its remaining time in the new template.
- **Alert overlay** (`/overlay/alerts/`):
  - Playback: follows, new subs, resubs, gift subs, Bits and raids (from Twitch or the simulator) go into the shared presentation queue (`core`'s `presentation`; alerts and stamp cards share one queue, played one at a time in arrival order, with no limit): after publishing an `alert` event, it waits for that alert's play time (6 seconds; 9 seconds for a resub or cheer with a message) plus 1 second before playing the next item in the queue; when an item's turn comes and no overlay of its kind is connected (see the WebSocket connection counts), it is skipped without waiting, except for items from the simulator (the admin window's preview still needs to receive them); the payload's `durationMs` tells the overlay how long to show it. For a gift, Twitch also sends one `channel.subscribe` (`is_gift`) per recipient; those do not play, only the gift itself does. While the module is disabled, alerts reaching the front are dropped. The queue status (the item playing, the waiting items, the gap) is published as the `presentation.queue` event; snapshots keep only the latest one, and the queue area on the admin UI's home page shows it and counts down roughly how long the wait is. `POST /api/admin/queue/clear` cancels the waiting items, and the one playing finishes; `POST /api/admin/queue/stop` (emergency stop) also stops the one playing and publishes `presentation.stopped`, on which every overlay removes its picture and stops its sound at once. Neither affects redemption or check-in records.
  - Templates: built-in only, `default`, `banner` and `text` (sources in `apps/web/src/overlay/alerts/templates/<id>/`, HTML/CSS only, also embedded in the executable); there are no folder templates. The choice is kept as `alert_template` in `settings.json` (default `default`; unrecognized values count as `default`); the admin UI reads and switches it with `GET`/`PUT /api/admin/templates/alerts` (`{ "selected": "<id>" }`; any other value gets 400 `template.unknown`, a failed save 500 `settings.save_failed`), and after saving the Host publishes `template.changed` (`overlay` is `alerts`) so overlays switch at once. `GET /templates/alerts/{*path}` serves the selected template and `GET /templates/built-in/alerts/{id}/{*path}` any of them for previews (unknown IDs get 404); both use the same type allowlist, path checks and headers as the chat templates. Binding: a `data-alert-stage` element (the alert playing now goes in it) and a `<template data-alert>` (the markup for one alert); `data-field="title"` gets who did what, `data-field="message"` the viewer's message (removed when there is none); the top element gets `data-kind` (the alert kind) and the CSS variable `--duration`, and is removed when that time is up. Text always goes in through `textContent`; the overlay parses with `DOMParser` and removes active content in the same way, and relative paths point into the template folder.
  - Sound: the default `chime.wav` is synthesised by `scripts/generate-chime.mjs` with Node's built-in modules only (no downloaded audio; recorded in `assets/CREDITS.md`), bundled into the build. Each kind can pick, on the alerts full page, the built-in sound (the default), a sound from the library, or silence (see "Sound library"); the payload's `sound` tells the overlay which (`built_in`, `silent`, or `file` with `url` and `volume`), played once as each alert starts. OBS browser sources may autoplay; to set its volume in the OBS mixer, check "Control audio via OBS" on the source.
- **Stamp card overlay** (`/overlay/checkin/`): for every successful check-in (repeats excluded), a card goes into the same presentation queue, and when its turn comes one `checkin.stamped` is sent: the viewer's name, avatar URL, current stamps and total slots, cumulative check-ins, whether the card was just filled, and how long to show it (5 seconds, then a 1-second gap before the next); not kept in snapshots. The avatar is looked up once on Twitch (Helix Get Users) and stored; only `https://static-cdn.jtvnw.net/` URLs are accepted, and the overlay checks again. The name is shown through Vue's text interpolation. The check-in settings can pick a library sound for a normal check-in and for a full card (silent by default); the payload's `sound` (`url`, `volume`; `null` when silent) plays once with the card. There is one built-in design (CSS only, no external assets), with a different effect when the card fills up. The simulator (`POST /api/admin/simulate/checkin`, `source=simulation`) reaches only the overlay and writes no records.
- **Sound library** (sound module): admin API `GET`/`POST /api/admin/sounds`, `PUT`/`DELETE /api/admin/sounds/{id}`.
  - Import: the body is the file itself, with the original file name in `?name=`; at most 10 MB (`DefaultBodyLimit`; larger gets 413 `sound.too_large`). The extension and the magic bytes at the start of the file must name the same format: MP3 (`ID3` or an MPEG frame sync), WAV (`RIFF`…`WAVE`) or OGG (`OggS`); otherwise 400 `sound.unsupported_type`.
  - The file is copied into the data folder's `sounds/`, named by a UUID v7; the original file name is only a label (shown as text), never a path. Label, volume (0–100%) and format are kept in `settings.json` under `sound.library`. Deleting removes the entry from `settings.json` first, then the file.
  - `GET /sounds/{id}` is read-only and needs no token (for overlays and the admin UI's preview). It serves only IDs in the library, and the file path is built from the ID and format alone. `Content-Type` is fixed by format (`audio/mpeg`/`audio/wav`/`audio/ogg`), plus `X-Content-Type-Options: nosniff` and `Cache-Control: no-store`.
  - Choosing what plays where: `PUT /api/admin/sounds/slots/{slot}` (`{ "sound": "<id>" | "silent" | null }`; `slot` is `alert.<kind>`, `checkin`, `checkin.full` or `reward.<Twitch reward ID>`), kept in `settings.json` under `sound.slots`; `null` goes back to the default (the built-in sound for alerts, silence otherwise). The alerts and checkin modules ask the sound module's public service only when they publish an event, so alerts and check-ins from the simulator play the chosen sound too. While the sound module is disabled, every slot plays its default.
  - Deleting a sound puts the slots that used it back to their defaults; each sound in `GET /api/admin/sounds` carries `used_by` (the slots that use it), which the admin UI lists before deleting.
- **Reward sound overlay** (`/overlay/sound/`): the sounds full page can map channel point rewards (the same list as the check-in settings, Helix Get Custom Reward) to library sounds. The Host hands each new redemption (`RedemptionChange::Added`) to the sound module at the same place it hands it to the redemption module (in memory, not through the outbox: a sound played late is worse than none, so redemptions from before a restart never play); the sound module puts it into the shared presentation queue (the same one as alerts and stamp cards), holding it for the sound's length; when its turn comes it publishes `sound.play` (`url`, `volume`), not kept in snapshots. A sound's length is stored in its library entry (`duration_ms`): after an import, the admin window reads the length with `<audio>` and saves it with `PUT /api/admin/sounds/{id}/duration` (1 millisecond to 6 hours); when the admin window opens, it also measures sounds that have no length yet. Until a length is measured, 5 seconds is used. The overlay plays them one at a time in the order they arrive, starting the next when one ends (or fails); beyond 100 waiting, the oldest is dropped. "Play in OBS" (`POST /api/admin/sounds/{id}/play`) skips the queue and reaches the overlay at once (`source=simulation`), writing no redemption record. Add this URL in OBS as a browser source with "Control audio via OBS" checked.
- **Host header**: accept only `127.0.0.1:<port>` and `localhost:<port>`, to block DNS rebinding.
- **Origin**: every WebSocket connection (overlays included) and every state-changing request checks Origin, accepting only `http://127.0.0.1:<port>` and `http://localhost:<port>` (current port); dev mode also accepts the Vite dev server origin (passed in by `apps/desktop` as runtime configuration). WebSocket connections without an Origin or with `Origin: null` are always rejected.
- **CORS**: none on `/api`, `/ws` and `/admin`. Only the build `assets/` directory (chunks shared by the admin UI and overlays) and the template paths (`/templates`, built-in templates included) send `Access-Control-Allow-Origin: *` (without credentials; the content is public code and templates), because the preview iframe's origin is `null` and Vite's module scripts, CSS and fonts must load through CORS.
- **Overlays**: routes are read-only, can only read snapshots and subscribe to public events, and have no state-changing endpoints; OBS URLs contain no token.
- **OBS Dock**: not done for now; its pairing will be designed later together with mobile remote control.

### Twitch rate limits
Twitch's official documentation is the source for these numbers; update this section when Twitch changes them.
- **Helix API**: a token bucket per client ID and user, refilled every minute (for example 800 points; most endpoints cost 1 point per call). Every Helix request goes through the one Helix client in `integrations`: a 401 gets one refresh and one retry; a 429 waits until `Ratelimit-Reset` (at most 1 minute) before trying again and is never resent right away. Some 429s are unrelated to the points bucket (for example EventSub limits); without `Ratelimit-Reset`, normal backoff applies. A Helix or OAuth request with no answer within 15 seconds counts as unreachable (`twitch.unreachable`), so nothing hangs.
- **EventSub WebSocket**: per user token (client ID and user), at most 3 connections with enabled subscriptions, at most 300 subscriptions per connection, and a `max_total_cost` of 10. The app opens only 1 connection per account and closes the old one before changing the Client ID or signing out; on `session_reconnect` it moves to the reconnect URL Twitch sends (this is not a new connection; subscriptions carry over and are not created again); failed connections reconnect with exponential backoff (from 1 second, at most 60 seconds).
- **Live state and stream sessions** (stream module): subscribes to `stream.online` and `stream.offline` (no authorization needed; each costs 1 of the `max_total_cost`), and only a start whose `type` is `live` counts; while signed in it also checks with Helix Get Streams every 60 seconds (once right after signing in), which picks up a stream that started before the app started or while EventSub was disconnected, and updates the viewer count. Each Twitch stream is one session, stored in `stream_sessions` (the Twitch stream ID is the unique key, so receiving the same stream twice counts as one session; the start time is Twitch's); after the stream ends, that session remains the current one until the next stream starts; opening a new session ends any other session not yet ended (a missed `stream.offline`, e.g. the app was closed during the stream and reopened during the next one) at the new stream's start time. Signing out of Twitch makes the state `unknown` and leaves the sessions as they are (signing out does not prove the stream ended). Get Streams lags behind the events by about a minute, so: when a check still lists the stream already ended by `stream.offline`, no session is reopened; a stream that started before the current session (a late check or event) is always ignored, and an older session never ends one that started later; when a check says there is no stream, only a session that started more than 3 minutes ago counts as ended (making up for a missed `stream.offline`). The state is published as the `stream.status` event (`state` is `unknown`/`offline`/`live`; while live it also carries `startedAt` and `viewers`), and snapshots keep only the latest one; the admin UI's top bar shows 「直播中」 (live), the duration and the viewer count, or 「已下播」 (ended), from it. Each session also stores its peak viewer count (the larger value at each check while live), kept across restarts.
- **This stream's stats** (composed by the Host): `GET /api/admin/stream/summary` returns the latest session (the live one, or after it ends the last one until the next starts) with its start and end times, peak viewers, and the follows, subs (new subs and resubs, each sub a gift hands out included), bits, raids and redemptions in it; `null` before the first session. Each module counts in its own table (activity records by session ID, redemption records by the session's time range), with no join across modules; `endedSinceLaunch` says the session ended after this launch. The stage card at the top of home switches by itself from `stream.status` and this summary: 直播中 while live; 下播後 with this stream's summary for a stream that ended after this launch; 開播前 otherwise (after a restart, signed out, or no Twitch stream). The broadcaster can switch to another stage to look at it until the state next changes. While live, the numbers are read again every 30 seconds.
- **Activity records** (activity module): each follow, sub, resub, gift (including each sub it hands out), cheer and raid from Twitch is stored as one row in `activity_events`, with the session ID at the moment the event arrived (the stream module answers in arrival order, so an event right after a stream start always counts toward the new session; no join across modules); the EventSub message ID is the unique key, so a redelivered notification is stored once; simulated events are not stored. The record retention is stored in `settings.json` as `record_retention` (`{"days": N}` with N from 1 to 3650, or `"forever"`; when unset it is 30 days, later shared with chat logs), and records past it are deleted at start and once a day; when `settings.json` cannot be read or holds an invalid value, nothing is deleted that time, rather than guessing from the default. Admin API: `GET`/`PUT /api/admin/records/retention` (`PUT` deletes the records the new retention no longer keeps in one database transaction, commits it only after `settings.json` is saved, and returns how many it deleted; if saving fails, the delete is cancelled too; after an error the admin UI reads the retention actually in effect again) and `GET /api/admin/records/expired?days=N` (how many records changing to N days would delete); before shortening the retention, settings 「資料與備份」 shows how many records will be deleted and asks to confirm. The records are in the database, so they are exported and restored with backups.
- **Viewer directory** (viewers module): one row per Twitch user seen in chat, alerts or redemptions, stored in `viewers` (the Twitch user ID is the primary key, so a renamed user updates the same row): login, display name, avatar, the roles shown by their chat badges the last time they chatted (broadcaster, moderator, VIP, subscriber; only chat carries badges, so other events do not change roles), and when they were first and last seen. For a viewer without an avatar it is looked up once on Twitch (Helix Get Users), and only `https://static-cdn.jtvnw.net/` URLs are stored (sharing the check and the lookup interface in `core` with check-ins). Simulated events never create or change viewers; check-ins' own viewer data is not moved over.
  - Each connection subscribes to 9 events: `channel.chat.message`; `channel.follow` (v2), `channel.subscribe`, `channel.subscription.message`, `channel.subscription.gift`, `channel.cheer` and `channel.raid` (with the `to_broadcaster_user_id` condition) for alerts; `channel.channel_points_custom_reward_redemption.add` and `.update` for redemption records. Raids need no authorization by the broadcaster and cost 1; the others are authorized by the broadcaster and cost 0, well under 10 in total.
  - When a sign-in from before an update lacks the scope an event needs, that event is not subscribed; when Twitch answers a subscription other than chat with an error status (including 429, or a channel without channel points), only a warning is logged and chat and the other events carry on. Only a failed chat subscription, or any subscription that encounters an invalid sign-in or cannot reach Twitch, counts as a failed connection and reconnects.
- **Device Code Flow**: poll at the `interval` Twitch returns until `expires_in`, never faster, and at least 1 second apart.
- **Sending chat messages**: nothing sends chat messages yet. When sending is added later (for example check-in replies), messages must be queued and rate-limited locally, using the conservative value of 20 messages per 30 seconds. Twitch allows 20 messages per 30 seconds for regular accounts and 100 per 30 seconds for the broadcaster, moderators and VIPs (messages from the broadcaster still count toward the 20-message bucket); going over makes Twitch ignore the account's messages for 1 hour.

### OBS connection
- `obws` connects to obs-websocket 5, which is built into OBS, without TLS. The address is stored in `settings.json` as `obs.host`/`obs.port` (default `127.0.0.1`/`4455`); the password is stored in the Windows Credential Manager, wrapped in a `SecretString` as soon as it is read, and never written to `settings.json` or logs; with no password set, the app connects without authentication (a normal state when OBS has authentication turned off). The handshake sends only the challenge response, never the password itself.
- Streaming-software interface: the state of scenes, items, inputs and outputs is defined in `core`'s `streaming` (`StreamingState` and the `StreamingSoftware` trait), and OBS is just one implementation of it; later features such as scenes and modes go only through this interface, never using `obws` directly. For now it only reads state; commands such as switching scenes, showing items or muting are added when a feature needs them.
- After connecting, it first reads the full state once (the current scene, each scene's items and whether they are shown, whether each input is muted, whether OBS is streaming and recording), then updates it from OBS events: scene switches, item visibility, mute, and streaming and recording state are updated in place; when scenes, items or inputs are added, removed, renamed or reordered, it reads everything again. Items inside groups are not listed. On disconnect the state is cleared (the scene is `null`, meaning unknown) and read again after reconnecting. The state is published as the `obs.state` event, whose `payload` is the whole state; the admin UI's top bar shows 「串流中」 (streaming) and 「錄影中」 (recording) from it.
- When the connection fails or drops, it reconnects with exponential backoff (from 1 second, at most 60 seconds, the same as EventSub); after a successful connection the backoff starts again from 1 second. Each connection attempt (including the handshake and version check) takes at most 10 seconds.
- Status (event `obs.status`; its `payload` holds `state` and `reason`; `reason` is a stable code, and `null` when `connected` or right after startup):
  - `connected`: connected.
  - `reconnecting`: not connected yet, or a state that recovers on its own, for example OBS is not running (`obs.unreachable`), OBS was closed (`obs.disconnected`), or the connection opened but the handshake failed or did not finish in time (`obs.handshake_failed`, for example when the other side is not obs-websocket). OBS not running is a normal state, not an error.
  - `error`: still retrying, but the user has to fix something, for example a wrong password (`obs.auth_failed`), OBS requires a password but none is set (`obs.password_required`), or an unsupported version (`obs.unsupported_version`; OBS 30.2 or later and obs-websocket 5.x at 5.5 or later are required).
- Logs record only status changes, so OBS staying closed for a long time does not keep writing logs.
- Admin API `/api/admin/obs`:
  - `GET` returns the address, whether a password is set (`password_set`; the password itself is never returned) and the current status; if the Credential Manager cannot be read, it returns 500 `obs.secret_store_failed`.
  - `PUT` changes the address and password (an omitted `password` keeps the stored one, an empty string deletes it) and reconnects with the new settings right away, clearing the old connection's scene and output state; the replaced connection no longer writes any state. The host accepts only host names and IPv4 addresses, and the port must not be 0; otherwise it returns 400 `obs.invalid_address`.
  - `PUT` saves `settings.json` before writing the password: if writing the password fails, the new address still takes effect and it returns 500 `obs.secret_store_failed`; if `settings.json` cannot be saved, it returns 500 `settings.save_failed` and the address, password and connection all stay as they were.

## 6. Host lifecycle
The Host runs in the Tauri process. Closing the admin window only hides it to the system tray and overlays keep running; closing the small port-change page also keeps the app in the tray; only Quit in the tray stops the Host.

When ✕ is clicked on the admin window, Rust always calls `prevent_close()`: if "Don't show again" is already stored in `settings.json`, the window is hidden right away; otherwise Rust sends an event to the admin window to show a hint, and the frontend reports "shown", "cancel" or "hide" with the app command `close_hint`; "hide" also carries the "Don't show again" checkbox value, which Rust writes to `settings.json`. If "shown" does not arrive within 2 seconds, or ✕ is clicked again while the hint is open, the window is hidden directly so that ✕ never appears to do nothing. "Ask before closing the window" under Settings → General changes the same value (admin API `GET`/`PUT /api/admin/general`; `ask_before_close` is the opposite of "Don't show again"); Rust rereads `settings.json` on every ✕, so a change applies immediately.

### Data directory
Each data directory is a separate app instance, identified by its `instance-id`: settings, logs, cache and WebView2 data all live in it. The app ships as a portable package only, so data defaults to the `data` folder next to the executable.
- Which data directory is used: the one given by `--data-dir <path>` on the command line; otherwise the `data` folder next to the executable (dev builds too, so theirs is `target\debug\data\`).
- Contents: `settings.json`, `logs/` (JSON, rotated daily, kept 14 days), `cache/`, `templates/` (`custom` templates, never created by the Host), `sounds/` (imported sounds), `WebView2/`, `instance-id`, `toolkit.db` (the database), `backups/` (backups taken before upgrades and restores); a restore also uses the temporary `restore-staging/`, `restore-pending` and `restore-previous/` (see "Backup files" below).
- Only one instance may run per data directory; different data directories can run side by side (for example to test a new version). `instance-id` is a random ID inside the data directory and survives moving it; a copied data directory keeps the same `instance-id`, counts as the same instance and cannot run next to the original. A new `instance-id` is made only when the file does not exist (`create_new`, so two copies starting together get the same ID); any other read error is shown and the app exits instead of switching to a new ID.
- Twitch sign-in and the OBS password are per data directory: the Credential Manager entries are named `<instance-id>/twitch` and `<instance-id>/obs`.
- If the data directory is not writable, show an error and exit; never fall back to another location.
- Side-by-side copies: extract the package more than once, or point `--data-dir` at different directories. There is no installer (see "Distribution" in decisions.en.md).

Backup files (`.stbackup`, "Backup and restore" on the settings page):
- A zip file holding `settings.json`, the database `toolkit.db`, `templates/`, `sounds/` and `manifest.json`; never `logs/`, `cache/`, `WebView2/`, `backups/` or `instance-id`. Twitch sign-in and the OBS password live in the Credential Manager, not in the data directory, so they never go into a backup; the Client ID is not a secret and is backed up with `settings.json`.
- The database is first saved as a snapshot in `cache/` with `VACUUM INTO`, then added to the zip; the open file is never read directly. Exporting during a stream leaves chat, alerts and check-ins running; database writes wait only while the snapshot is taken.
- `manifest.json`: `format` (`streamer-toolkit-backup`), `format_version` (currently 1), `app_version`, `schema_version` (the newest migration applied to the database, 0 for an empty one), `created_at` (UTC, RFC 3339), `records` (`redemptions`, `checkins`: how many redemption and check-in records there are), `files` (each file's `path`, `size` and `sha256`).
- Paths may only be `settings.json`, `toolkit.db`, or relative paths under `templates/` or `sounds/`, separated by `/`; no segment may be empty, `.` or `..`, contain `\`, `:` or other characters Windows does not allow, or be a reserved name (`CON`, `NUL` and so on). Symbolic links and junctions are not backed up.
- Limits: a 512 MB zip, 10,000 files, 2 GB in total once extracted. An export over a limit is refused (413 `backup.too_large`), so every exported file can be restored.
- Export: the admin API `GET /api/admin/backup` returns the backup file. The admin UI first opens a save dialog (`showSaveFilePicker`) to choose where, then writes the response there; without that API the browser downloads the file instead.
- A restore replaces everything; it never merges:
  1. Choosing a file: the admin UI sends the file as-is to `POST /api/admin/backup/restore/preview` (at most 512 MB, `DefaultBodyLimit`). Before anything is written, it is checked in memory: the limits, every path, each file's size and SHA-256 (reading at most one byte more than the manifest says; the zip's own size fields are never trusted), and that the zip holds exactly the listed files plus the manifest. A `format_version` or `schema_version` newer than this version answers 400 `backup.newer_version`; any other mismatch answers 400 `backup.invalid`. Once it passes, it is extracted to the data directory's `restore-staging/`; then the database itself is checked (every applied migration must be one this version knows, with the same checksum and finished; an unknown one also answers `backup.newer_version`) and `settings.json` must parse. Only then is `manifest.json` written, marking the staging complete, and a preview returned (backup time, app version, redemption and check-in record counts, number of template folders, number of sound files). Any failing step deletes `restore-staging/`; the data in use is never touched.
  2. Confirming: `POST /api/admin/backup/restore` (409 `backup.nothing_staged` when nothing is staged) writes `restore-pending` (holding a new ID for this restore), answers 202, then restarts the app (`AppHandle::request_restart`, keeping the command-line arguments).
  3. At startup (see "Startup order"): the current data is first saved as `backups/before-restore-<UTC time>.stbackup` (which can be restored the same way later); then the current `settings.json`, database (with `-wal` and `-shm`), `templates/` and `sounds/` move into `restore-previous/` and the staged ones move into place (renames inside the data directory; before anything moves, `restore-previous/` gets the same restore ID); then the normal database open runs (backing up first when migrations are pending). If any step fails, the contents of `restore-previous/` go back into place, the reason is shown and startup continues; on success a notice says the backup holds no Twitch sign-in or OBS password, so sign in again and re-enter it when needed. Finally `restore-pending`, `restore-previous/` and `restore-staging/` are deleted; the restore ID and the staged `manifest.json` go first, so if `restore-pending` cannot be deleted (the error is shown and the user is asked to delete it by hand), the next start neither puts old data back nor applies the restore again.
  - If the app ends in the middle of the moves, the next start finds both `restore-pending` and `restore-previous/` with the same restore ID, puts the original data back first and explains that the restore was interrupted. A `restore-previous/` with another ID (or none) was left by an earlier restore that had finished, and its data was backed up to `backups/` then: it is never put back, and is deleted before the new restore is applied. If even that fails, both are kept, the error is shown and the app exits; the next start tries again.
  - Staged but never confirmed: the next start just deletes `restore-staging/`.
  - `instance-id` is not in the backup and does not change on restore; the Credential Manager entries are named after it, so restoring into another data directory or another PC means signing in to Twitch and entering the OBS password again.

Startup order:
1. Resolve the data directory and check that it is writable. `tauri-plugin-single-instance` names its lock after the identifier, so at startup the identifier gets the `instance-id` appended and the lock is per data directory. Register this plugin first, so a second copy never tries to take the port before handing off.
2. Apply a confirmed restore first (see "Backup files"), then open the database and apply migrations; both come after the single-instance lock, so a second copy never touches the same data directory.
3. The Host binds the port; on failure, open the small port-change page and retry after the user saves.
4. Release build: create the remote capability for the current port, then create the admin window and load the Host URL. Dev mode: the admin window loads the Vite dev server and uses capability 2.
5. Before creating any window, check that the WebView2 Runtime is present (built into Windows 11; missing on a few Windows 10 PCs). If it is missing, show an explanation and open Microsoft's download page; the Host, overlays and tray keep running, and after installing it, choosing Open in the tray creates the window without a restart.

## 7. Enforcing the rules
- Cross-module dependencies: enforced by each crate's `Cargo.toml`.
- Layer rules: architecture tests (`crates/arch-tests`) run in CI. They check that `domain/` contains no occurrence of `sqlx`/`axum` at all (including `use`, derives and full paths), that code in `application/` (outside comments and tests) never uses `infrastructure` (publishing and other adapters are injected by infrastructure as callbacks), and use `cargo metadata` to check dependency direction: modules may depend only on `core` and other modules, never on `integrations` or `host`; `core` depends on no other workspace crate; `integrations` depends only on `core`; only `integrations` may depend on external platform SDKs (`obws`, `tokio-tungstenite`). Module internals are always `pub(crate)`, so other modules see only each other's public interfaces; Cargo itself forbids dependency cycles, and when one appears the shared types move to `core`.
