# Development

## Environment (Windows)
- Rust: version pinned by `rust-toolchain.toml`.
- Node: 24 LTS, in `.nvmrc`. Tauri CLI and lefthook are pnpm devDependencies, run with `pnpm tauri …` and `pnpm lefthook …`. pnpm: install once with `npm i -g pnpm`; it then switches versions according to `packageManager` in `package.json`, without Corepack; dependencies are locked by the lockfile; install with `pnpm install --frozen-lockfile`.
- Visual Studio Build Tools (MSVC) and WebView2 Runtime (required by Tauri).
- `cargo-deny`: `cargo install --locked cargo-deny` (the pre-push hook and CI both run `cargo deny check`).
- Playwright's Chromium (for UI E2E): `pnpm --filter web exec playwright install chromium`, once; the browser goes in the user profile, not the repo.
- sccache (optional): shares compiled Rust dependencies across all worktrees, so a new worktree's first build is faster (shared dependencies are not rebuilt; each worktree's own crates and build-script output still compile). Builds work without it.
  - Install: `cargo install --locked sccache`, then in PowerShell run `[Environment]::SetEnvironmentVariable('RUSTC_WRAPPER', 'sccache', 'User')`; it takes effect in a new terminal. `sccache --show-stats` shows the hit rate.
  - Set it only in your own environment variables, never in the repo's `.cargo/config.toml`. Before removing sccache, run `[Environment]::SetEnvironmentVariable('RUSTC_WRAPPER', $null, 'User')` in PowerShell and open a new terminal, or cargo fails to find it and builds break.
  - The cache defaults to `%LOCALAPPDATA%\Mozilla\sccache`, capped at 10 GB (change with `SCCACHE_CACHE_SIZE`). Each worktree still has its own `target\` (dev data lives in `target\debug\data\`); only the cache is shared.

Principle: another Windows PC can get it running by following this document.

## Common commands
- Install dependencies: `pnpm install --frozen-lockfile`
- Build the frontend: `pnpm web:build` (required before the first Rust build; the Host embeds `apps/web/dist` into the executable)
- Develop: `pnpm tauri dev` (Vite hot reload), or `cargo run -p desktop`
- API contracts: after changing the Host's HTTP API or WebSocket events, run `pnpm api:gen` (build the frontend first). Rust (`utoipa`) writes `apps/web/src/api/openapi.json`, then `openapi-typescript` writes `schema.d.ts`; commit both files. CI fails when regenerating changes them. The WebSocket snapshot and event types are also OpenAPI components, and tests compare them with the JSON actually sent; when you add an external event or a snapshot-retained event type, also add its type to the components in `crates/host/src/openapi.rs`.
- Checks: `pnpm web:lint`, `pnpm web:test`, `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`, `cargo deny check`; UI E2E runs separately (see "Testing baseline" below); to run the same steps as CI (also covering translations, script tests, frontend licenses, the frontend build, API contracts and release clippy), use `pnpm lefthook run pre-push --force` (without `--force` it skips steps based on the pushed files; see "Git" below)
- Data: dev builds keep their data in `target\debug\data\` and never touch other copies' data; to test with another set of data, add `--data-dir <directory>` and set the environment variable `DEV_DATA_DIR` to the same directory's absolute path (the Vite proxy of `pnpm tauri dev` reads the port from there; without it, from `target\debug\data\`). Logs are in the data directory's `logs\` (JSON); use `RUST_LOG=debug` for more detail.
  - Dev builds default to port `47811` in a new directory, while release builds use `47810` (which OBS browser sources point at), so with the release build closed, OBS never connects to a dev build. A port already saved in an existing `target\debug\data\settings.json` is not changed; to switch to the dev default, edit `port` by hand or delete that file. Scripts that write `settings.json` before starting a dev build must write `port` themselves, or the release default applies.
  - Dev builds open only folders they created: they put a `dev-folder` marker in `target\debug\data\` and in new or empty folders; when `--data-dir` points at a non-empty folder without the marker (such as release data), they exit without writing anything, because once in-progress migrations are applied, the release build can no longer open that database. Scripts that write settings before starting a dev build must create `dev-folder` too. To use such a folder anyway, add `--allow-release-data` (every time); a copied release folder keeps the same `instance-id`, so it shares the original's tokens in Credential Manager.
- Testing without OBS or Twitch (fake services, `crates/fakes`):
  - `pnpm dev:fake` starts the fake OBS (`127.0.0.1:4466`), the fake Twitch (`127.0.0.1:4467`) and a dev build; the data directory is `target\dev-fake-data\` (port `47812`), made fresh on every run, or kept from the last run with `--keep`. The app starts signed in to the fake Twitch and connected to the fake OBS.
  - Control panel: `pnpm dev:fake` also opens a small window (always on top, can be turned off) with the app's connections on the left, tabs on the right and the activity log at the bottom; `Ctrl` with `+`, `-` or `0` zooms in, out or back. Closing the panel ends the run; add `--no-ui` to go without it. On its own: `cargo run -p fakes --features ui -- --ui` (the panel is built only with the `ui` feature).
  - Sending events: `cargo run -q -p fakes -- send <kind> [--user <login>] [--count <n>] [--message <text>] [--reward <reward title>] [--bits <n>] [--tier 1000|2000|3000] [--months <n>]`. Kinds: `follow`, `sub`, `resub`, `gift` (plus one `sub` per recipient), `cheer`, `raid`, `chat` (`--first` adds the first-chat mark), `delete`, `clear-user`, `clear`, `redeem`, `redeem-update` (`--id` and `--status fulfilled|canceled`), `online`, `offline`. Events go through the real connection flow (`source=twitch`) and reach that directory's business records.
  - Other commands: `obs drop` (OBS disconnects; the app reconnects on its own), `obs stats [--cpu <%>] [--dropped <%>] [--kbps <n>]` (the performance page uses a 60-second window, so after setting dropped frames back to 0 the warning goes away only once the window average falls to 5% or below), `obs stream on|off`, `obs record on|off`, `eventsub drop`, `scenario stream-start|stream-end|gift-bomb|redemption-flood`. For another port, use `--port <fake Twitch port>`.
  - API call statistics: `stats [--reset] [--json]` lists every kind of call the app makes to the two fakes (Helix paths, OBS requests, WebSocket connections): counts, per-minute average, peak in 10 seconds, average and shortest gap, handling time, requests in flight; calls and reaction time after each kind of event; Helix use against the 800-point bucket and how often `/validate` runs; and warnings (identical requests within 1.5 seconds, a loop of 5 under 1 second apart, more than 10 calls per event, more than 4 requests in flight, reconnects without backoff, missing headers or an unknown token, no token check for over an hour). Warnings only list things; they fail nothing. `--reset` starts over after listing. The thresholds are constants in `crates/fakes/src/metrics.rs`.
  - Making an API fail or slow down: `fault "<call>" [--status <code>] [--delay <time>] [--for <time>] [--close]`; `fault --clear` removes them all. Calls are written as in `stats` (`GET /helix/users`, an OBS request type, `ws-connect eventsub|irc|obs`), times like `500ms`, `3s` or `2m`, 1 minute by default; for a connection, `--close` drops it at once and refuses new ones. Meanwhile `stats` lists the retries after each failure and their gaps, and warns when the gaps do not grow at least 1.5 times each time (up to 55 seconds) or there are more than 20 retries.
  - Load runs: start `e2e_host` in fake-services mode (`E2E_ADMIN_TOKEN=<random> E2E_FAKE_SERVICES=127.0.0.1:4467 E2E_FAKE_OBS_PORT=4466 cargo run -p host --example e2e_host -- <port> <temp directory>`) and `fake-services`, then run `node scripts/bench.mjs <scenario> --host 127.0.0.1:<port> --fake 127.0.0.1:4467 [--duration <s>]` (with the same `E2E_ADMIN_TOKEN`). Scenarios: `idle` (no events for 10 minutes, to see how often the app calls the APIs on its own), `chat` (50 chat messages a second), `gifts` (100 gifted subs at once), `redemptions` (200 redemptions), `obs` (30 extra sources sending audio meters every 50 ms, 20 scene switches, 20 sources added and removed), `all` (chat, redemptions and the OBS load at once). The report goes to `target\bench\` (Markdown and JSON): chat latency from sending to the overlay receiving it (median, p95, maximum) and anything missing, how long the alert queue took to drain, whether every redemption was recorded, the app's CPU and memory, and the `stats` for that time. It is not in CI and has no thresholds; run it before and after a change to compare. The OBS meter load and bursts can also be triggered by hand with `fake-services obs meters [--inputs <n>] [--interval <ms>]` and `obs burst scenes|items [--count <n>]`.
  - The fake OBS alone: `cargo run -p fakes`, then point OBS in the settings at `127.0.0.1:4466`; `--password <password>` makes it ask for authentication.
  - A dev build switches to the fake Twitch through `TOOLKIT_FAKE_SERVICES=127.0.0.1:<port>` (see "Data directory" in [architecture.en.md](architecture.en.md)); `e2e_host` uses `E2E_FAKE_SERVICES=127.0.0.1:<port>` and `E2E_FAKE_OBS_PORT=<port>`.

## Git
- The repo is public: anyone can see the code and commit history.
- Commit author email uses the GitHub noreply address: `git config user.email "<id>+<username>@users.noreply.github.com"` (this repo only).
- Branches and PRs: `main` is the default branch; work on a branch, open a PR, and rebase-merge it after CI passes (`gh pr merge <number> --rebase`). The repo allows only rebase-merge, so `main` stays one straight line.
  - Exactly one Conventional Commit per issue. Before pushing, combine an issue's work into one commit locally, leaving no fixup or review-fix commits in the PR: use `git reset --soft`, or `git commit --fixup` then `GIT_SEQUENCE_EDITOR=: git rebase -i --autosquash` (the environment does not support interactive rebase).
  - An issue must fit in one commit. A broad issue becomes a parent issue with GitHub sub-issues: each sub-issue is one commit, and the parent gets no commit and closes once all sub-issues are done. If an issue turns out too big partway through, stop and propose a split to the user instead of letting the commit grow.
  - One PR may hold several independent issues from the same stage, one commit each, with the PR description listing `Closes #…` for each. Issues that touch the same files are done in sequence on the same branch, never in parallel.
  - To keep a branch current with `main`, use `git rebase origin/main` then `git push --force-with-lease` (on your own branch only); never merge `main` into the branch, because merge commits make rebase-merge fail.
- Hooks: lefthook, configured in `lefthook.yml`, with `assert_lefthook_installed` on, so a missing lefthook fails the commit instead of silently skipping checks.
  - lefthook is a pnpm dev dependency; the `prepare` script in the root `package.json` runs `lefthook install`, so hooks are enabled after `pnpm install`, without relying on package postinstall scripts.
  - Hooks check the working tree, not the staged snapshot; CI runs the same check again on the pushed commit.
  - `pre-push` runs the checks in CI order (which steps it skips is below; translations, script tests, frontend licenses, frontend lint/test/build, API contracts up to date, `cargo fmt`, both `cargo clippy` runs, `cargo test`, clippy and tests for the fake-services control panel (the `fakes` `ui` feature), `cargo deny check`; not UI E2E) and blocks the push at the first failure, so failures surface before CI. Keep the `pre-push` steps in `lefthook.yml` in sync with `.github/workflows/ci.yml`; change one, change the other.
  - `pre-push` runs only the steps the pushed files can affect. The rules are the same as CI's (see "Before every commit"), but exclude lists cannot express exceptions, so a push may run more than CI, never less:
    - Docs only (root `*.md`, `docs/`): only the translation check; a change to `docs/decisions.md` also runs the script tests and the frontend license check (the license allowlist lives in that file).
    - Frontend only (`apps/web/`): skips `cargo fmt`, both `cargo clippy` runs, the fake-services control panel and `cargo deny check`; the rest runs. Changes limited to the admin UI (`apps/web/src/admin/`), interface text (`apps/web/src/locales/`) or E2E (`apps/web/e2e/`) also skip `cargo test`; other frontend changes run it, because the Host embeds `apps/web/dist`, and the Rust tests also check the overlay page and the built-in templates (`apps/web/src/overlay/chat/templates/`, `apps/web/src/overlay/alerts/templates/`).
    - Rust only (crates other than `crates/host/`, `Cargo.*`, `rust-toolchain.toml`, `deny.toml`): skips the script tests, the frontend license check and frontend lint and test; the frontend build and the API contracts still run (Rust needs `dist`). `crates/host/` and `apps/desktop/` still run these checks, because they hold files that frontend or script tests read. Changes limited to `crates/host/`, `crates/modules/` or `crates/arch-tests/` skip the fake-services control panel.
    - Any other file (`lefthook.yml`, `.github/` and so on): everything runs. Changes limited to `package.json`, `pnpm-lock.yaml` or `scripts/` skip the fake-services control panel.
    - Files are compared with the remote branch (for a new branch, `origin`'s default branch); lefthook does not list paths that no longer exist (a renamed file may not appear at all), so a push that only deletes or renames files may skip checks, and CI catches it.
- Line endings are normalized by `.gitattributes` (LF; CRLF for Windows scripts).

## Before every commit (PR CI runs the same set, Windows only)
Order: build the frontend first (`dist/` is not under version control, and `rust-embed` needs it to compile), then run the Rust checks.
CI runs only on PRs; merging into `main` does not run it again, because rebase-merge lands exactly the commits the PR already checked. After a merge into `main`, `cache.yml` only compiles, without checks, and saves the Rust and pnpm caches on `main`; PRs restore from `main` and never save their own (per-PR caches would evict main's). When GitHub updates the runner image's Rust, the cache no longer matches; until the next merge, trigger `cache.yml` by hand.
CI is split into jobs: `changes` decides from the PR's files which jobs to run; `web` always runs the translation check and the other frontend checks only when needed; `rust` runs the Rust checks alongside it, builds the frontend itself (the Host embeds it) and leaves the typecheck to `web`; `fakes-ui` runs the control panel checks alongside both with its own cache (iced stays out of the main one); `check` only confirms that every job that had to run passed and that only jobs known to be unneeded were skipped, and is the only check the `main` ruleset requires. CI builds keep line numbers only (`CARGO_PROFILE_DEV_DEBUG=line-tables-only`): faster links and a smaller cache, while panics still show file and line. `ci.yml` and `cache.yml` must set it alike, or the cache never matches.
Formatting, lint, type checks, tests, architecture tests and `cargo deny check` (licenses and security advisories), `pnpm check:licenses` (frontend licenses) and `pnpm test:scripts` (Node tests for `scripts/`) all pass (Rust: `cargo fmt --check`, `cargo clippy`, `cargo test`; frontend: lint, typecheck, test, build); generated OpenAPI and TS types must be up to date.
Cargo commands without `tauri/custom-protocol` all compile in dev mode, so CI also runs `cargo clippy --features tauri/custom-protocol` to check code compiled only in release (for checking only; nothing is distributed). Releases always use `tauri build`.

Jobs CI skips by the files changed (rules and reasons in `scripts/ci-changes.mjs`; any other or unknown file runs everything):
- Docs only: only the translation check.
- Only the admin UI, interface text (`apps/web/src/locales/`) or E2E: skips `rust` and `fakes-ui`.
- Rust only: `web` runs only the translation check. The exceptions are five Rust-side files that frontend or script tests read (`crates/host/src/lib.rs`, `apps/desktop/src/main.rs`, `apps/desktop/src/data_folder.rs`, `apps/desktop/tauri.conf.json`, `apps/desktop/Cargo.toml`); when a Rust change touches the API, the PR must update `apps/web/src/api/` too, and `web` runs as well.
- Only `apps/`, `scripts/`, `crates/host/`, `crates/modules/`, `crates/arch-tests/` or frontend config files: skips `fakes-ui`.
- Any change to `.github/` or `scripts/ci-changes*.mjs`: everything runs.
- `changes` first runs `scripts/ci-changes.test.mjs`: it scans the code to confirm that the files the frontend and Rust read from each other match the rules; write such a read as a literal path string, or the test cannot find it.

## Releasing
Only the portable zip is released. Pushing a `v*` tag makes `.github/workflows/release.yml` build it:
1. Run UI E2E (`e2e.yml`) first; if it fails, nothing is released.
2. The build job has read access only, and its checkout keeps no GitHub credentials; it first checks that the tag's commit is on `main`, then checks that the tag matches the version in all three of `apps/desktop/tauri.conf.json`, `apps/desktop/Cargo.toml` and `package.json` (`node scripts/check-version.mjs <tag>`); if not, nothing is released.
3. Generate `THIRD_PARTY_LICENSES` (see "Licenses"; `cargo-about` is pinned), then run `pnpm tauri build --no-bundle`.
4. Pack `streamer-toolkit-<version>-windows-x64.zip`: it holds a single `Streamer Toolkit\` folder with `Streamer Toolkit.exe`, `LICENSE`, `THIRD_PARTY_LICENSES` and `使用說明.txt` (from `apps/desktop/release/usage.zh-TW.txt`), never `data`; a `.sha256` goes next to it.
5. A separate job downloads the built zip and `.sha256` and creates a draft release (`gh release create --draft`). The workflow never publishes; only this job has `contents: write`, and it runs no build code.

Steps: bump the version in all three places through a PR and merge it, then tag `v<version>` on `main` and push the tag; when the workflow is done, download the draft's zip from GitHub Releases, verify the checksum, extract and start it on a Windows machine without developer tools, and only then publish.

## File length
A soft limit, not checked in CI. Whether to split a file depends on how many reasons it has to change; the line count is only a reminder.
- When production code passes about 800 lines, or a test file about 1000 lines, consider a split first the next time an issue changes that file; if it should be split, open a separate issue instead of folding the split into the current commit.
- Split by responsibility (for example `routes.rs`, `repo.rs`), not at an arbitrary line count.
- When a single function passes about 100 lines (the default of clippy's `too_many_lines`), consider a split the same way: extract steps that can be named on their own, or repeated setup, into functions. A test function that walks through a whole scenario may be longer, but repeated setup steps still go into helpers.
- When Rust tests get too long, move them into a `tests` submodule (`#[cfg(test)] mod tests;`, with the contents in `<module>/tests.rs`, or by topic in `tests/<topic>.rs`). They stay in-crate unit tests so they can use private items. Do not give a submodule the same name as a crate-root module or a dependency crate; it would shadow the item of that name brought in by `use super::*`.

## Testing baseline
- Test only the behavior we own, not Twitch/OBS themselves.
- Levels: unit tests for domain/use cases; integration tests for Repositories and HTTP against a real SQLite; contract checks that generated files are up to date; UI E2E for browser behavior jsdom cannot test.
- UI E2E (`apps/web/e2e/`, Playwright + Chromium):
  - When it runs: not in PR CI or pre-push (it is the slowest step). Trigger the "UI E2E" workflow (`.github/workflows/e2e.yml`) by hand in GitHub Actions; the release workflow also runs it before building the zip and does not release if it fails. When you change the admin UI, overlays or E2E tests, run it locally once before pushing. Rust and frontend unit and integration tests still gate every PR, because they guard the data rules.
  - Running locally: `pnpm web:build` first (the Host embeds `apps/web/dist`), then `pnpm web:e2e`; install Chromium the first time (see "Environment" above).
  - The admin UI runs on the Vite dev server, with the admin API replaced by `page.route`, `/ws/overlay` by `page.routeWebSocket` and Tauri IPC by the fake `invoke` in `e2e/fixtures.ts`; fixtures contain only a dummy token, never a real token or secret; Vite sends the same CSP as the Host, so E2E runs under it (the header the Host actually sends is covered by the `crates/host` Rust tests). Drawer behavior no real feature uses yet (settings fields, dropdowns, "Open full page") is tested on the test page in `e2e/harness/`.
  - The overlay is tested against a real Host: `crates/host/examples/e2e_host.rs` starts the Host in a temporary data directory (random admin token, fake secret storage, Twitch and OBS both pointed at an address nothing listens on). These tests share one Host, are tagged `@host` and run one at a time in the Playwright `host` project; the other tests run in parallel in the `admin` project.
  - Logic that unit tests can cover still gets unit tests; E2E does not repeat them.
- Architecture tests (`crates/arch-tests`): `domain/` contains no occurrence of `sqlx`/`axum` at all; `application/` does not use `infrastructure`; crate dependencies point the right way: modules depend only on the shared core (`crates/core`, package name `toolkit-core`) and other modules' public interfaces, never on `integrations` or `host`; modules do not use other modules' non-public types (rules in [architecture.en.md](architecture.en.md)).
- Migration test: merged versions are globally unique and sorted.
- Must test: redemption deduplication and state transitions, restoring a backup actually works, migrations lose no data.
- Test with simulated events instead of real Twitch triggers. Simulated events are tagged `source=simulation` and must never be written to any real business records (redemption records, check-in records).
- a11y baseline: every action can be done with the keyboard, focus is visible, every control has a label, text contrast meets WCAG 2.2 AA (4.5:1), control boundaries and informative icons reach 3:1 (WCAG 1.4.11), and status is never conveyed by color alone. No screen reader testing, but semantic markup and ARIA are still done properly.
- Checked automatically by UI E2E (on manual runs and before a release):
  - Drawer: at window widths above 1000px, the drawer (380px wide) sits side by side with the tiles, which stay usable; at or below 1000px it is a modal on the right that closes on a backdrop click or Esc; below 600px it comes up from the bottom.
  - After crossing the 1000px width threshold, the drawer stays open and focus, input values and scroll positions are preserved.
  - On open, focus is on the close button; after closing, focus returns to the tile, status light or pending item that opened it (the home page has no pending items yet, so a stand-in on the test page is used); if that item is gone, it falls back to its tile (the further fallbacks, the first tile and then "Edit home", are covered by unit tests).
  - After typing without pressing Enter, leaving the drawer in each of these ways has saved the value: ✕, Esc and "Open full page" (once side by side and once modal), plus another tile when side by side and a backdrop click when modal.
  - When a save fails, the drawer stays open, the field returns to the old value and the error is shown; if the failure happened when the field lost focus, the first ✕ press afterwards still keeps the drawer open (a second press closes it).
  - When the drawer is modal, error messages and its buttons are visible and can be pressed; with a dropdown open inside the drawer, Esc closes only the dropdown, not the drawer.
  - At window widths of 1280px, 640px and 320px (equivalent to 1280px zoomed to 200% and 400%) there is no horizontal scrollbar; the home page's keyboard path works end to end: skip link (focus lands on the first tile), open the drawer, send a simulated chat, close the drawer (1280px and 800px).
  - The close-hint `<dialog>` (with fake IPC): the actions sent to Rust are correct when pressing Esc to cancel, clicking "Got it", and checking "Don't show again".
  - Editing home: an emptied home stays empty after a reload, and "Edit home" brings a tile back; focus on entering, hiding, adding back and leaving; with a drawer opened in edit mode (side by side and modal), the first Esc closes only the drawer and the second leaves edit mode; no horizontal scrollbar at 1280px, 640px and 320px; when a save fails, the tile goes back where it was and the error is shown.
  - Full pages (⚙ Settings): entering focuses the header's first button, or the title when it has none; the 首頁 tab and Back (Alt+←) both return home, and Back does not grow history; back on home, focus returns to ⚙ (returning to the tile after a drawer's "Open full page", and the further fallbacks, are covered by unit tests), and the drawer does not reopen.
  - On the settings page, a field typed into without pressing Enter is saved when leaving with the 首頁 tab or Back; when the save fails, the page stays and shows the error; when the window gets focus again, "Ask before closing the window" is read again.
  - The template picker on the chat full page: clicking a preview picks that template and saves it; arrow keys move the pick; a failed save goes back to the template in use and shows the error; no sideways scroll at 1280px and 320px.
  - Alert simulator: each of the six kinds is sent once with the right name, amount and message; a refusal shows its reason; no sideways scrolling at 1280px, 640px and 320px; the real Host sends every simulated kind to `/ws/overlay` as an `alert` marked `source=simulation`, answers 400 to an amount out of range and 401 without the admin token.
  - Alert overlay (real Host, shorter play time): the six kinds play one at a time in the order sent, each with a sound, and leave when their time is up; a gift of 3 subs plays once; picking a built-in template switches it at once, without a reload.
  - Stamp card overlay (real Host, shorter show time): simulated check-ins show one card at a time in the order sent, a just-filled card shows the full-card effect, each leaves when its time is up, and nothing is written to check-in records; the check-in simulator in the drawer sends the right name and stamps.
  - Alerts full page template picker: every preview plays the sample alert; clicking a preview picks and sends it; arrow keys move the pick; no sideways scrolling at 1280px and 320px.
  - Redemption records: the tile shows the latest one and the drawer lists the most recent ones, with viewer text never treated as HTML; the full page sends the right filters and pages, and on `redemption.changed` reads again with the same filters and page; with no records it shows an empty state; a rejected query shows why; no horizontal scrollbar at 1280px, 640px and 320px.

## Hard security and data constraints (never skip)
- HTTP/WebSocket bind to `127.0.0.1` only, never the LAN.
- The admin API requires the random token generated at every launch, delivered to the admin window over IPC and kept in memory only, never in localStorage; check the Host header and Origin; the admin window and the API share one origin, so there is no CORS; the admin window may only navigate to `/admin` paths, and `/admin` sends a strict CSP (details in [architecture.en.md](architecture.en.md)).
- Overlay routes are read-only, never get OAuth tokens, and cannot call the admin API.
- User templates and overlays are never rendered directly in the admin window; previews go in an iframe with only `sandbox="allow-scripts"` and receive data via `postMessage`.
- Escape all viewer input, such as chat messages and display names, to prevent XSS.
- Tokens are stored in Windows Credential Manager (entries kept separate per data directory) and wrapped in `SecretString` in code; never in logs, plaintext files or backups.
- The repo is public: never commit secrets, tokens or personal data. Twitch uses the Device Code Flow, so no client secret is needed; each user registers their own Client ID and stores it in settings; it is never built into the repo.
- Redemption events are deduplicated by Twitch redemption ID.
- Back up the database automatically before migrations; no operation may silently delete data.
- Times are always stored in UTC; "daily" features (such as check-ins) use the time zone set by the streamer.

## Language
- `README.md` and `docs/` (including `docs/modules/`) are bilingual: Traditional Chinese is the only authoritative version, and the English version is `<name>.en.md` in the same folder. `docs/archive/` is not translated. `AGENTS.md` is English only.
- Write Chinese only while working; English need not keep pace. **Before committing docs**, generate or update the English versions using an AI-assisted command, then have a human review them before committing.
- If Codex CLI is installed, you may optionally have it review the translation before the human review. Codex sends the document contents to an external model service, so an AI agent must ask the user first and run it only with their consent. Run it only once, after the Chinese is final, and again only if the Chinese meaning changes: `codex exec -C . -s read-only --ephemeral -c model_reasoning_effort="medium" -o <report file> "<prompt>" < /dev/null`. The prompt names the authoritative file and the translation path, limits the review to the uncommitted diff, asks for additions, omissions and meaning shifts (especially numbers, negation, conditions and terms), forbids editing files, and asks for a report in Traditional Chinese with `file:line` and a paste-ready fix. Check each finding against the Chinese before applying it.
- Line 1 of an English file records `<!-- source: <path to Chinese file> source-sha256: <hash> -->`, line 2 is the language switch (`[繁體中文](<name>.md) | **English**`); the Chinese file starts with `**繁體中文** | [English](<name>.en.md)`. Document links inside English files point to the matching `.en.md`.
- `node scripts/check-translations.mjs` checks three things: every Chinese file has an English version, every English file's source points to its same-name Chinese file (no orphans), and each English hash matches its Chinese file; otherwise it fails and prints the problem file or the new hash.
- The pre-commit and pre-push hooks both run this check, and CI runs the same command; the hook only checks and never translates.
- Code: identifiers, comments, API/DB fields and error codes are always English. Error codes use `<area>.<reason>`, e.g. `twitch.sign_in_required`.
- Commits: English Conventional Commits, e.g. `feat(checkin): add daily check-in rule`.
- Fixed UI strings live in resource files, so translation later needs no component changes.
